# قبول مهمة واحدة عند إعادة إرسال الطلب

الحالة: واجهة محرك داخلية منفذة؛ نتائج الاختبارات الفعلية تسجل في حالة التنفيذ. ليست قناة IPC أو إضافة متصفح مصادقًا عليها.

## العقد

`Manager::enqueue_once(key, options, priority)` يقبل طلب إنشاء مهمة مع مفتاح إعادة إرسال. يتطلب مديرًا فتح طابورًا دائمًا بنجاح؛ المدير الموجود في الذاكرة يعيد `NotDurable` قبل إرسال أمر إلى العامل. التخزين الدائم يعتمد حاليًا حماية Windows DPAPI.

المفتاح من 1 إلى 128 بايت ASCII قابل للطباعة دون مسافات أو محارف تحكم. لا يظهر نصه في snapshots أو الأخطاء أو السجل. يجب على طبقة التطبيق ربط المفتاح بهوية المصدر المصرح له قبل الاستدعاء؛ امتلاك مفتاح ليس إثبات صلاحية، ولا تتحول هذه الواجهة إلى مصادقة للمتصفح.

أول قبول يحفظ المهمة وإيصالًا لها داخل **اللقطة المشفرة والمعاملة نفسها** قبل إقرار النجاح وقبل بدء عامل الشبكة. إذا انقطع انتظار المتصل أو فقد الرد بعد الحفظ، يعيد الطلب بالمفتاح والخيارات الأصلية نفسيهما؛ يحصل على هوية المهمة الأصلية دون مهمة أو تنزيل جديدين. إسقاط مستقبل انتظار الرد لا يلغي أمرًا وصل إلى المدير.

| حالة إعادة الإرسال | النتيجة |
| --- | --- |
| المفتاح والخيارات والأولوية الأصلية مطابقة | هوية المهمة الأصلية، حتى بعد إعادة فتح البرنامج |
| المفتاح نفسه مع محتوى طلب مختلف | `IdempotencyConflict` |
| مهمة أزيلت من القائمة باستخدام `forget` | `PreviouslyRemoved` عند إعادة الطلب الأصلي؛ لا يعاد إنشاؤها |
| مدير غير دائم | `NotDurable` |
| مفتاح غير صالح | `InvalidIdempotencyKey` |
| امتلاء سجل الإيصالات بمفتاح جديد | `ReceiptCapacity` |

يبقى الإيصال مرتبطًا **بطلب القبول الأول**. تغيير السرعة أو الأولوية أو تجديد الرابط بعد القبول لا يعيد كتابة بصمته. إعادة إرسال الطلب الأول تعيد الهوية؛ إعادة إرسال إعدادات المهمة المعدلة تحت المفتاح القديم تعد تعارضًا. يجب أن يحتفظ المتصل بخيارات القبول الأصلية عند إعادة الإرسال.

## الهوية والتخزين

يحفظ الإيصال SHA-256 منفصل النطاق للمفتاح وللمحتوى، وهوية المهمة وعلامة الإزالة. بصمة المحتوى تشمل جميع حقول `Options` والأولوية، بما فيها بيانات الاعتماد وCookie والأصول المسموحة للتحويل وبصمة الرابط السابق واسم الملف والمسار وحدود النقل. تستخدم الحقول النصية أطوالًا صريحة وقيمًا محددة للأنواع الاختيارية والأولوية، فلا تختلط حدود الحقول.

يطبّع الرابط بمحلل URL الموجود في الناقل. يطبّع المسار المطلق من مكوناته دون قراءة نظام الملفات، ويحافظ على حالة الأحرف؛ لا يتطلب تكرار طلب مقبول وجود الملف أو المجلد وقت الإعادة. اختلاف تهجئة حالة المسار قد يعد محتوى طلب مختلفًا. فحوص المسار الفعلية والتكرار المعتادة لا تزال تجرى عند قبول مهمة جديدة.

تستخدم لقطة الطابور v3 مع قراءة v1 وv2 القديمة دون اختلاق إيصالات لطلبات لم تحفظها. تحفظ الإيصالات مع لقطة المهام والإعدادات قبل النجاح؛ فشل الحفظ يغلق القبول ويلغي العمال وينتظر انتهاءهم كما في عقد المدير. لا تعني بصمة المحتوى تشفيرًا منفصلًا، ولهذا تبقى الإيصالات داخل اللقطة المشفرة أيضًا.

سقف سجل الإيصالات **4096 قبولًا مميزًا طوال عمر الطابور**، مستقل عن سقف المهام الحالية. لا حذف تلقائي أو إخراج لأقدم إيصال. الإزالة من القائمة تحفظ علامة إزالة، والعداد العام للمهام لا يعود للخلف. فحص إيصال موجود يسبق فحص السعات ومسارات الملفات، لذلك يظل رد الطلب المقبول أو المزال متاحًا عند امتلاء السجل. إدارة أرشيف السجل أو تدويره سياسة مستقبلية، ولا يجوز تنفيذها بحذف إيصالات صامت يسمح بالتكرار.

تنسيق بصمة الطلب v1 وترميز الخيارات `encode_options_v2` مجمدان باختبار بصمة ثابتة. إضافة حقول للخيارات مستقبلًا تحتاج تنسيقًا ذا إصدار ومسار توافق للإيصالات السابقة؛ لا يجوز تغيير البصمة القديمة بإعادة استخدام الإصدار نفسه.

## الاختبارات والحدود

اختبارات `admission.rs` تغطي إعادة متزامنة وفتح المدير مجددًا وتعارض الإعدادات وعلامة الإزالة وفشل الحفظ ورفض المدير غير الدائم. اختبارات داخل المدير تغطي فقد متلقي الرد قبل معالجة الأمر، والسعة 4096 دون حذف الإيصالات، وتأثير كل حقل على البصمة. اختبارات المخزن تغطي قراءة الإصدارات القديمة والبصمة المرجعية ورفض إيصالات مكررة أو ذات هوية غير متسقة.

الضمان محلي للطابور الذي بقيت بياناته سليمة. حذف الطابور أو استبداله بنسخة أقدم أو امتلاك الحساب الذي يحمي DPAPI خارج هذا الضمان. اختبار فقد الرد داخل العملية لا يعادل فصل طاقة أثناء SQLite، ولا يمثل إثبات exactly-once عبر منظومة موزعة. لا يستبدل الإيصال التحقق من الرابط والصلاحية وموافقة المستخدم قبل بدء التنزيل.
