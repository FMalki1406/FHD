# مراجعة معمارية المحرك وخطة المعالجة

التاريخ: 2026-09-21. الأساس المفحوص: `3914b12` بعد نجاح CI السابق. هذه مراجعة للكود وتصميم أعمال لاحقة، وليست تنفيذًا للمعمارية الجديدة أو قياس أداء. المراجعة المقدمة من المستخدم أساس هذه القائمة؛ فحص Engineering وSecurity يكملها.

## القرار

تُقدّم معالجة مسار البيانات والمتانة على توسيع واجهة المستخدم وتكامل المتصفح. نجاح اختبارات الصحة السابقة لا يثبت كفاءة الملفات الكبيرة أو جاهزية enterprise. لا يقتصر العلاج على زيادة حجم RANGE_BYTES؛ يجب فصل حجم طلب HTTP عن حجم مخزن الذاكرة وحجم الكتابة ووحدة الإقرار الدائم.

## نتائج التحقق

| الموضوع | ما يثبته الكود | القرار |
| --- | --- | --- |
| النطاقات والموجات | `parallel.rs` يطلب 256KiB، يجمع موجة كاملة ثم يرتبها ويكتبها. 10GiB تعني 40960 طلب نطاق في النجاح المعتاد، إضافة إلى طلب الاستجابة الأول؛ 10GB عشرية نحو38147 نطاقًا. | أولوية P0: تخزين موضعي وخريطة تقدم، وعمال مستقلون. لا ادعاء بقياس منافسة IDM من هذه الحسابات. |
| الاستجابة الأولية | تبقى استجابة GET الكاملة أو بقية الاستكمال مفتوحة حتى يثبت أول طلب نطاق دعم206. يحدث تداخل للبيانات المطلوبة، وليس بالضرورة إعادة تنزيل الملف كاملًا على الشبكة؛ مخازن الشبكة قد تقرأ مسبقًا. | probe محدود يمكن استهلاك بياناته، مع مسار200 تسلسلي واضح. | الكتابة | مسارا الطول المعروف والمجهول ينسخان كل شريحة pacing ثم ينقلان Store إلى spawn_blocking. حجم الشريحة قد يصل بايتًا. | P0: مالك كتابة واحد، قناة محدودة بالبايتات، تجميع مستقل عن pacing. عند1B/s لا يعني ذلك آلاف استدعاءات القرص في الثانية؛ المشكلة فصل المسؤوليات وكلفة الاستدعاء لكل شريحة، وتحتاج قياسًا. |
| تنظيم النقل | `download_controlled` يجمع التحقق والاستعادة والطلب والقرار والنقل والنشر. checkpoint والخروج وحلقة الجسم مكررة؛ لدى unknown helper محلي بالفعل. | تقسيم validate/recover/probe/plan/transfer/commit وإعادة استخدام stream pump دون توحيد خاطئ لشروط known/unknown/range. |
| المدير | معالجات طويلة داخل select، وبحث Vec متكرر؛ next_eligible يمسح المهام لكل مرشح ويحسب إشغال الأصل مجددًا. | ManagerState، معالجات أوامر، جدول بالهوية وطوابير FIFO مستقلة حسب الأولوية وعدّادات أصل؛ لا الاعتماد على ترتيب HashMap للإنصاف. |
| المؤقت | tick كل100ms يُستخدم لنشر التقدم ولإعادة فحص retries. | sleep_until لأقرب retry، ومؤقت مستقل محدود لنشر التقدم؛ إزالة tick بالكامل تفقد تحديث التقدم. |
| حفظ الطابور | لقطة لكل المهام والإيصالات، تشفير ومعاملة كاملة لكل تغيير دائم؛ actor ينتظر spawn_blocking. | كتابة تغييرات معاملية عبر مالك تخزين مستقل. الطلب لا يقرّ قبل commit. نقل العمل إلى thread وحده لا يلغي انتظار actor أو تضخيم الكتابات. tick لا يحفظ تلقائيًا كل100ms في التنفيذ الحالي. |
| Proxy | ClientBuilder يستدعي no_proxy. | بوابة إطلاق: Direct/System/Explicit وسياسة مصادقة وثقة. يمنع البيئات التي تفرض proxy؛ لا يصح تعميم أنه يمنع كل مؤسسة. |
| الرصد والأخطاء | snapshots وأخطاء مصنفة موجودة، لكن لا pipeline تشخيص إنتاجي؛ Network يجمع أسبابًا مختلفة وDisplay يطبع التصنيف. | أحداث ومقاييس محدودة، وفئات timeout/connect/TLS/protocol/storage آمنة؛ لا حفظ reqwest::Error الخام الذي قد يتضمن الرابط. |
| السياسات الثابتة | timeouts وUser-Agent وredirects واحتياطي المساحة ثابتة. توجد حدود قابلة للضبط في Options/Config أيضًا. | سياسات مكتوبة ذات defaults وإصدار؛ ليست كل ثوابت السلامة اختيارًا للمستخدم، ولا تعرض أسرار أو تفاصيل داخلية في واجهة المنتج. |
| مشاركة العميل | Client جديد لكل محاولة تنزيل؛ clones داخل المحاولة تتشارك pool. | cache محدود للعملاء حسب سياسة proxy/TLS والشبكة، لا عميل عالمي يخلط هويات اتصال مختلفة. |
| أسرار الأنظمة | الطابور المشفر يدعم Windows فقط. | بوابة إطلاق: موفرو أسرار للنظامين الآخرين مع رفض آمن عند تعذر الخدمة؛ لا fallback plaintext. |
| Options والأسماء | مدخلات عامة والتحقق موزع، وفحص أسماء Windows مكرر. | تحويل RawOptions إلى ValidatedOptions مرة عند الحد؛ إعادة التحقق من القرص والاستجابة عند الاستخدام تبقى ضرورية. الحفاظ على توافق بصمات وإيصالات القبول القديمة. |
| الحالات | آلة Download محلية بهوية1 ومدير بحالات مهمة. | تحديد حالات المهمة مقابل محاولة النقل صراحة؛ إما ربط الدومين فعليًا أو إزالة تمثيله الشكلي. الهوية1 لا تتبادل أحداثًا بين المهام حاليًا، وليست دليل تصادم هوية بحد ذاتها. |
| قابلية الاختبار | اختبارات HTTP وقرص حقيقية كثيرة، مع اختبارات pure domain وحقن faults في Store أيضًا. | ports ضيقة للطلبات/الوقت/الكاتب عند الحاجة للمحاكاة، مع إبقاء اختبارات النقل والقرص الحقيقية. ليس صحيحًا أن كل اختبار يتطلب خادمًا وقرصًا. |

## ترتيب التنفيذ ومعايير الإغلاق

كل صف دفعة مستقلة قابلة للمراجعة؛ جميعها مفتوحة. P0 أولوية عمل، وليس ادعاء ثغرة أمنية حرجة.

| الدفعة | التنفيذ | دليل الإغلاق المطلوب |
| --- | --- | --- |
| A — مسار البيانات P0 | مخزن نطاقات بإصدار جديد، writer محدود، تخطيط نطاقات كبيرة متكيّف، عمال دون حاجز موجات، probe محدود | نطاق بطيء لا يمنع العمال الآخرين من سحب عمل جديد؛ استعادة بعد قتل عملية مع فجوات؛ رفض تبدل الهوية والتداخل والتجاوز؛ SHA نهائي مطابق؛ عددHTTP والذاكرة والكتابات مقاسة |
| B — تنظيم المحرك | ValidatedOptions وstream pump ومراحل النقل، مصدر حقيقة واضح للمهمة والمحاولة | بقاء حالات الإلغاء وclean EOF وpublication والاستكمال وبصمات القبول القديمة؛ اختبارات تميّز الطلبات الفاسدة قبل آثارها |
| C — إدارة وتشغيل الطابور | ManagerState وفهارس ومؤقتات deadline وتغييرات تخزين معاملية | 1024 مهمة و4096 إيصال تحت قرص بطيء، قياس زمن استجابة الأوامر وعددبايتاتDB؛ لا ACK/worker قبل الإقرار الدائم؛ سقوط أثناءcommit لا يكرر مهمة |
| D — الشبكة والتشخيص | client cache حسب السياسة، proxy، أخطاء آمنة، Retry-After+jitter، tracing/metrics | proxy authentication وتحويلات آمنة؛ إعادة استخدام اتصالات دون تسرب اعتماد؛ canaries للروابط/Cookie/Authorization/مسارات المستخدم في السجلات؛ سيناريو429 ينتظر مدةالخادم |
| E — المنصات والوجهات | موفرو أسرار، نشر no-replace للأنظمة المدعومة، دعمjunction مختار، Copy/Move واضحان | macOS/Linux secrets tests، رفض مخزن أسرار معطل، سباق إنشاء الوجهة دون overwrite، أنواع ملفات/أقراص مؤهلة فعليًا، crash-safe نقل دون فقد المصدر |

## خطة القياس

تُحفظ نتائج baseline والإصدار الجديد بنفس البيئة والمحتوى والسياسات: ملفات64MiB و1GiB و10GiB؛ اتصال واحد و4و8؛ RTT منخفض وعال؛ worker واحد بطيء؛ قرص بطيء؛ انخفاض سرعة1B/s وإلغاء. الحالات الكبيرة والسعة المطلوبة اختيارية في CI العادي وتعمل على runner مؤهل، وليست أمرًا بتنزيل بيانات عامة أو ملء قرص المستخدم.

نسجل throughput وCPU وpeak resident memory والبايتات المخزنة في القنوات وعددHTTP/TLS وعمليات الكتابة/fsync وبايتاتSQLite وزمنpause/إقرارالأوامر وكميةالعمل المعاد بعدrestart. معاييرالسلامة حاسمة دائمًا؛ أهداف الأداء العددية تعتمد بعد baseline موثق، ولا نخترع نسبة تسريع قبل القياس. الدليل الحالي64MiB لا يغطي هذا التأهيل.

## تصحيح مهم للنشر

لا يعتمد fallback على `exists()` ثم `std::fs::rename()`: يستطيع طرف آخر إنشاء الهدف بينهما، وrename قد يستبدله. المطلوب عملية نظام ذرية no-replace، أو فشل واضح عند عدم وجود ضمان مدعوم. لا حذف مقصد المستخدم لإجبار النجاح. توثيق [Rust rename](https://doc.rust-lang.org/std/fs/fn.rename.html) يوضح الاستبدال، وتوثيق [reqwest Client](https://docs.rs/reqwest/0.13.5/reqwest/struct.Client.html) يؤكد إعادة استخدام pool داخل العميل.
