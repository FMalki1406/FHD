# الموقع التجاري والدفع والتفعيل

التاريخ: 2026-09-21. القرار: الدفع يتم في الموقع، وليس داخل برنامج التنزيل، وفق توجيه المستخدم. الحالة: نطاق وتصميم؛ الموقع والدفع لم ينفذا بعد. مزود الدفع والأسعار ونموذج الاشتراك غير معتمدين.

## توزيع المسؤوليات

| المكون | المسؤولية |
| --- | --- |
| الموقع العام | تعريف المنتج، الميزات والمنصات المدعومة، الأسعار عند اعتمادها، تنزيل المثبتات الرسمية، الدعم |
| حساب العميل في الموقع | شراء الخطة، إدارة الاشتراك إن اختير، الفواتير، الأجهزة والاسترداد وفق السياسة |
| مزود الدفع | تجربة الدفع ومعالجة بيانات وسيلة الدفع عبر تكامل معتمد بعد اختياره |
| الخدمة التجارية | إنشاء طلب موثوق، التحقق من نتيجة الدفع، إدارة الاستحقاق وإصدار الرخصة |
| تطبيق سطح المكتب | تسجيل الدخول والتفعيل وعرض الرخصة وتحديثها؛ فتح الموقع في المتصفح الخارجي عند طلب الشراء أو إدارة الحساب |

لا نموذج بطاقة ولا Checkout مدمج داخل WebView التطبيق، ولا مفاتيح مزود دفع أو أسرار إصدار رخص فيه. الحساب في الموقع والتطبيق يشيران إلى نفس هوية العميل؛ لا تنشأ هويتان تجاريتان منفصلتان بالخطأ.

## رحلة الشراء

1. يختار المستخدم الشراء من الموقع مباشرة أو يفتح صفحة الخطط من التطبيق في المتصفح الخارجي.
2. يربط الخادم الطلب بحساب العميل وبنسخة الخطة والسعر والعملة من كتالوجه الموثوق. لا يعتمد قيمة سعر أو استحقاق يرسلها المتصفح.
3. ينشئ الخادم جلسة دفع مرتبطة بالطلب مع مزود الدفع المختار. يُعرض للمستخدم الحساب والخطة والشروط قبل التأكيد.
4. نتيجة العودة إلى صفحة النجاح تعني العودة من بوابة الدفع فقط؛ إذا لم يصل تأكيد موثوق تظهر «جارٍ تأكيد الدفع» مع إمكانية تحديث الحالة دون طلب دفع آخر.
5. تتحقق الخدمة من إشعار المزود أو نتيجة استعلام خادمي موثوق: مصدر الحدث، بيئة التشغيل، الطلب، الحساب، حالة الدفع، المبلغ والعملة. دلالات نجاح الدفع تحدد وفق المزود وطريقة الدفع؛ الدفع المعلق ليس نجاحًا.
6. تسجل الخدمة الحدث وتحدث الاستحقاق بطريقة تمنع الأثر المكرر، ثم تتيح الرخصة الموقعة للحساب الصحيح.
7. يسجل المستخدم الدخول في التطبيق أو يختار تحديث حالة الرخصة؛ يحصل عليها من خدمة الاستحقاق المصادقة. لا يلزم أن يكون التطبيق مفتوحًا وقت الشراء.

زر العودة للتطبيق اختياري لاحقًا. رابط النجاح أو deep link ليس دليل دفع ولا يحمل رخصة أو access token أو refresh token. فتحه لا يمنح مزايا؛ التطبيق يعيد الاستعلام الآمن. تدفق تسجيل دخول المتصفح له تصميم مصادقة مستقل قبل تنفيذه.

## متانة تكامل الدفع

- حفظ معرفات الطلب والحدث وجلسة الدفع مع قيود تمنع التكرار. إشعار واحد يعاد إرساله لا يكرر الرخص أو المقاعد.
- لا افتراض لترتيب وصول الأحداث. لا يعيد حدث دفع قديم منح استحقاق ألغي أو استرد لاحقًا دون فحص الحالة المرجعية.
- حفظ الحدث بشكل متين قبل تأكيد استلامه للمزود، ثم معالجة قابلة لإعادة المحاولة. عند فصل المعالجة إلى مهام، نستخدم تسليمًا متينًا مع منع التكرار بدل الاكتفاء برسالة في الذاكرة.
- مهمة مصالحة تعالج انقطاع الإشعارات والطلبات العالقة بالاستعلام عن الحالة لدى المزود. تمنع المعالجة المتزامنة تضاعف الأثر.
- فصل حالات الطلب والدفع والاشتراك والاستحقاق؛ ليست boolean واحدة. فشل إصدار الرخصة بعد دفع مؤكد يظهر كحالة معالجة ودعم، لا سبب لدفع جديد.
- الإلغاء والتجديد والاسترداد والاعتراضات المالية لها سياسة انتقالات صريحة قبل البيع؛ لا حذف لملفات العميل بسبب أي منها.
- سجلات الدعم لا تحمل بيانات بطاقة أو أسرار جلسة أو سجل تنزيلات. لا نزعم نطاق امتثال أو شهادة قبل تحديد المزود والتكامل ومراجعتهما.

## مراجعة Engineering وSecurity

راجع الوكيلان فصل الموقع والتطبيق في 2026-09-21، وأضيفت الضوابط التالية إلى التصميم قبل التنفيذ:

- التحقق من توقيع webhook عبر أداة المزود المعتمدة وبالجسم الأصلي عند اشتراطه، مع حدود إعادة الإرسال وفصل بيئة الاختبار والإنتاج وحساب التاجر. لا اعتماد على البريد في callback لإثبات ملكية الطلب.
- منع التكرار يشمل معرف الحدث ومعرف عملية الدفع والطلب، لا معرف الحدث وحده. التصميم المرجعي inbox دائم ومعاملة لتغيير الحالة وoutbox لإصدار الاستحقاق؛ توقيع الرخصة لا يلزم داخل طلب webhook نفسه.
- نطاقات العودة محددة مسبقًا، ولا إعادة توجيه إلى عنوان يختاره العميل بحرية. تسجيل الدخول في المتصفح الخارجي يتطلب تصميم state/nonce وPKCE عند اعتماد OAuth؛ رابط عودة تسجيل الدخول منفصل عن إثبات الدفع.
- الموقع مستقل في تجربة العميل ويمكنه مشاركة خادم تجاري واحد بوحدات واضحة. لا حاجة لخدمات مصغرة لمجرد نقل الدفع إلى الموقع.

المراجع التي استخدمها المراجعان: [Webhooks الرسمية لدى Stripe](https://docs.stripe.com/webhooks) كمثال على متطلبات مزود، وليس اختيارًا له، و[RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) للمصادقة في التطبيقات الأصلية. التفاصيل النهائية تتحقق مقابل المزود الذي سيُختار.

## معايير قبول الموقع والدفع

| المعرف | الدليل المطلوب قبل الإطلاق |
| --- | --- |
| WEB-01 | لا تدفق دفع داخل التطبيق؛ زر الشراء يفتح الوجهة الرسمية المسموحة في متصفح خارجي |
| WEB-02 | تعديل الرابط أو سعر الطلب أو خطة المتصفح لا يغير السعر أو يمنح استحقاقًا |
| WEB-03 | إشعار مزور أو بيئة خاطئة أو مبلغ/عملة/طلب غير مطابق لا يمنح رخصة |
| WEB-04 | تكرار الإشعار وتزامنه ووصوله بترتيب مختلف ينتج استحقاقًا متسقًا واحدًا |
| WEB-05 | إغلاق المتصفح أو التطبيق وفقد إشعار ثم المصالحة لا يفقد شراء مؤكدًا ولا يطلب الدفع مجددًا |
| WEB-06 | حساب آخر لا يرى الطلب أو الفاتورة أو الرخصة؛ تطابق العميل يراجع خادميًا |
| WEB-07 | تأخر التأكيد وفشل الدفع والإلغاء والاسترداد لها رسائل وإجراءات متسقة مع الاستحقاق |
| WEB-08 | شراء من الموقع ثم تثبيت التطبيق وتسجيل الدخول يفعّل الخطة الصحيحة؛ deep link مزور لا يفعّل شيئًا |

ترتبط هذه المعايير بـPR-026 وDL-020 وDL-021 وبوابة G4، وتكمل [تصميم الترخيص](licensing-and-tamper-resistance.md). لا تغير هذا القرار مدة التجربة أو السعر أو تفرض اشتراكًا دوريًا.

## رحلة العميل

توثيق نقاش التثبيت، التجربة دون حساب، نقل التفعيل إلى جهاز آخر والاستجابة للاشتباه في العبث في [رحلة التثبيت والتفعيل](customer-installation-and-activation.md). أرقام 14 يومًا و3 أيام وجهازين مقترحات منتج، وليست خططًا منشورة أو ضوابط منفذة.
