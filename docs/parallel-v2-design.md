# تصميم النقل المتوازي v2: أجزاء مستقلة وتخزين نطاقات

الحالة: تصميم مقترح بعد مراجعة الشفرة، **غير منفذ وغير متحقق منه**. المرجع الحالي `download-engine/src/parallel.rs` و`transfer-store/src/lib.rs`. هدفه إزالة حاجز النوافذ دون التضحية بالاستعادة أو حدود الذاكرة. ليس هذا وعدًا بتحسن سرعة على كل خادم.

## ما ثبت في التنفيذ الحالي

- `transfer` يجمع جميع نتائج نافذة من حتى ثمانية طلبات، ثم يرتبها ويكتبها بالتتابع. الجزء البطيء يؤخر حفظ الأجزاء الأخرى وبدء النافذة التالية؛ لا يعاد ملء مكان العامل المنتهي فورًا.
- `Fetch::range` يجمع حتى 256 KiB في Vec لكل طلب. الحد الحالي محدود ومعقول، لكنه مرتبط بتجميع النافذة وليس تدفقًا إلى كاتب دائم.
- خطأ طلب يلغي بقية عوامل النافذة وينتظر خروجها. الأجزاء الناجحة داخل النافذة التي لم تكتب تفقد، ويظل الاستكمال بادئة متصلة فقط.
- `Store` يملك مؤشر ملف متتابعًا و`len/committed` وSHA-256 تراكميًا واحدًا. `open` يتحقق من البادئة ويقصر ما بعدها. هذا السلوك صحيح للمخطط الحالي، لكنه **غير صالح** لخريطة نطاقات قد تحوي أجزاء سليمة بعد فجوة.
- قبل المسار المتوازي يوجد GET عادي، وتبقى استجابته مفتوحة أثناء طلب أول نطاق، ثم تُسقط عند نجاحه. لا يستهلك التطبيق الجسم الكامل مرتين، لكن الخادم وHTTP/TLS/النظام قد ينقلون أو يخزنون بايتات من الاستجابة الأولى بلا استخدام. لا يجوز تسويق ذلك باعتباره probe بلا نقل زائد.
- يكرر النشر الحالي قراءة الملف للتحقق من البصمة عبر مراحل متعددة. تغيير خريطة الأجزاء لا يبرر إزالة تحقق النشر أو الاكتفاء بحجم الملف.

## قرار المعمارية المقترح

منسق واحد لكل مهمة يملك جيل التمثيل وجدول النطاقات وتوزيع العمل. عوامل HTTP مستقلة تبث قطعًا محدودة إلى **كاتب واحد** يملك الملف وSQLite طوال حياته. يحفظ الكاتب نطاقًا اكتمل قبل غيره فور أهلية checkpoint، دون انتظار نهاية نافذة. يعاد ملء مكان كل عامل من قائمة العمل المتبقية بعد إقراره؛ لا تستخدم نافذة ثابتة.

المرحلة الأولى من v2 تبقي عدد عوامل الملف بين 1 و8. وحدات الاستعادة المقترحة 4 MiB، والقطع العابرة لقناة الكاتب حتى 64 KiB. تثبيت هذه القيم قرار تجريبي يحتاج قياسًا، وليس نتيجة benchmark. الملف الذي تجاوز الحد المعتمد لعدد وحدات الاستعادة يرفض قبل إنشاء المخزن؛ اقتراح البداية 262144 وحدة وبحد حجم 1 TiB، أو حد المستخدم الأصغر. لا تنشأ قائمة بايتات بحجم الملف.

توضع حصة أصل/مضيف مشتركة على مستوى طلب HTTP في المنسق العام، بما فيها probe والتحويلات والمحاولات. حصة المهام الحالية لا تكفي؛ ثماني مهام بثمانية عوامل تعني حتى 64 طلبًا. يعاد حجز حصة الوجهة عند التحويل دون الاحتفاظ بحصة أصل سابق أثناء انتظار الجديدة، لتجنب deadlock. تستعمل جميع العوامل محدد سرعة المهمة والمحدد العام، وتراقب عدالة الانتظار بقياس فعلي.

## اكتشاف الإمكانات دون GET كامل مهمل

طلب الاكتشاف الأساسي المقترح `GET Range: bytes=0-0`، مع identity والتحقق المعتاد للرابط والسياسة. لا يرسل GET كاملًا موازيًا لهذا الطلب، ولا ينشئ عاملًا آخر قبل تثبيت هوية التمثيل من الاستجابة:

1. عند 206 صالح، يؤخذ الحجم من Content-Range، ويتحقق من ETag قوي والترميز والطول واحد والنهاية السليمة. البايت الأول يصبح بذرة صالحة لوحدة التخزين الأولى، وتبدأ طلباتها التالية من البايت 1؛ لا يعاد طلب البايت الأول في المسار السليم. يبدأ بقية الملف بنطاقات غير متداخلة.
2. عند 200 تجاهلًا لـRange، **نفس الاستجابة** تصبح النقل الأحادي، معروفًا أو مجهول الطول حسب رؤوسها. لا يطلق طلب كامل ثانٍ ولا يفسر جسم 200 كنطاق.
3. عند 206 بلا ETag قوي لا نملك شرط ربط آمن بين طلبين: يُغلق الطلب ويبدأ نقل أحادي مستقل. النقل الزائد في التطبيق هنا محصور في probe واحد بايت، ولا ندعي حدًا دقيقًا على buffers الشبكة. لا يدمج ذلك البايت بتمثيل لم يثبت تطابقه.
4. حالة ملف فارغ 416 مع Content-Range `*/0` لا تكفي وحدها للنشر: يتحقق مسار صريح من استجابة GET فارغة سليمة؛ لا تنشر بناء على رأس خطأ.

HEAD خيار تحسين لاحق لبعض الخوادم، لا مصدر حقيقة بديلًا لفحوص GET. لا تُستخدم Accept-Ranges كدليل على تنفيذ النطاقات. إذا تغيّر التمثيل بين probe والعوامل، تفشل المهمة ولا تخلط البايتات. التحويلات والأسرار والأصول المسموحة تتبع السياسة نفسها لكل طلب.

## ثوابت التخزين والحالة

- كل رسالة تحمل `JobId + generation + range_id + attempt`؛ يرفض الكاتب رسالة من جيل أو محاولة ألغيت. الإزاحات نصف مفتوحة، بحسابات checked، وتحقق أن القطعة داخل النطاق المحجوز.
- لا يكتب عامل إلى نطاق حجزه عامل آخر، ولا يعاد فتح نطاق committed للكتابة داخل الجيل نفسه. لا توجد كتابات عشوائية مباشرة من عوامل HTTP.
- `received_bytes` تقدم شبكي متطاير. `durable_bytes` مجموع أطوال نطاقات committed غير المتداخلة، وليس أكبر offset ولا حجم الملف. يعرض كذلك `contiguous_prefix` للاستخدامات التي تحتاج بادئة، ولا يخلط معها المجموع.
- EOF نظيف ومطابقة مجموع طول الطلب شرط قبل اعتماد نطاقه. استقبال العدد المتوقع من البايتات وحده لا يكفي. نطاق اكتمل كتابةً قبل فشل framing يبقى غير معتمد ويعاد طلبه.
- الملف قد يكون ذا فجوات منطقية؛ طول `metadata.len()` لا يثبت اكتماله، وقد تكون الأصفار بيانات حقيقية. لا يستنتج الاكتمال من مواضع الأصفار أو تخصيص نظام الملفات.
- لا نعتمد دعم sparse allocation لنظام الملفات لإثبات صحة البيانات. الكتابة بعد فجوة ممكنة منطقيًا، وقد يخصص النظام مساحة فعلية؛ فحص المساحة تقديري، وخطأ امتلاء القرص يظل مسارًا واجب المعالجة.
- لكل نطاق معتمد SHA-256 محلي لكشف فساد القرص أثناء الاستعادة. ليست بصمات الأجزاء إثبات أصالة ولا يمكن جمعها لإنتاج SHA-256 الكامل؛ التحقق النهائي يقرأ الملف بالترتيب ويقارن البصمة الموثوقة إن وجدت.
- هوية المهمة تثبت الحجم والتمثيل وETag ومصدره وبصمة الرابط. تغير المورد لا يعالج بتصفير الحالات مع إبقاء أجزاء قديمة قابلة للاعتماد؛ يحتاج جيلًا جديدًا وسياسة إعادة بدء واضحة.

## عقد الكاتب المحدود

واجهة مقترحة، لا واجهة Rust منفذة:

| العملية | العقد |
| --- | --- |
| `open_or_create(identity, layout)` | قفل OS حصري، تحقق نسخة المخطط وهوية المورد وحدود الخريطة، ثم إرجاع ملخص النطاقات المتينة |
| `lease(range, generation, attempt)` | حجز نطاق غير معتمد وغير متداخل؛ token غير مشتق من مدخل متصفح |
| `write_chunk(token, offset, buffer)` | حتى 64 KiB، تسلسل صحيح داخل الطلب، backpressure قبل تخصيص buffer إضافي |
| `finish_response(token, verified_end)` | استلام تصريح نهاية من محول HTTP بعد الرؤوس والطول وEOF؛ لا يعني durable بعد |
| `checkpoint()` | fsync للملف أولًا، ثم معاملة SQLite تعتمد النطاقات المكتملة وبصماتها، ثم إقرار DurableRanges |
| `invalidate_attempt(token)` | يرفض الرسائل المتأخرة ويبقي البيانات غير المعتمدة خارج خريطة الصلاحية؛ لا يمس نطاقًا سبق اعتماده |
| `shutdown(mode)` | إيقاف الطلبات وقبول القطع، تصريف/إلغاء العوامل وفق الوضع، حفظ المكتمل الممكن، انتظار الكاتب وتحرير القفل أخيرًا |
| `verify_and_publish()` | تغطية كاملة دون فجوات أو تداخل، لا lease نشط، تحقق الملف الكامل، ثم نية نشر دائمة ونشر دون استبدال |

اقتراح حد قناة الكاتب 16 buffer × 64 KiB، مع buffer واحد إضافي بيد كل عامل بحد أقصى 8: **1.5 MiB لقطع التطبيق**. يشمل القياس أيضًا بذرة probe وأي buffer hashing منفصل. لا يشمل الرقم مكتبة HTTP وTLS والنواة أو جداول SQLite؛ تسجل هذه منفصلة في RSS. الحجز يكون بتصريح bytes من pool محدود قبل نسخ البيانات؛ عدد رسائل محدود وحده لا يحمي الذاكرة إذا سُمح برسالة بحجم غير محدود.

الكاتب blocking task طويل العمر واحد، وليس `spawn_blocking` جديدًا لكل 64 KiB. يملك SQLite وFile وعمليات seek/write أو محول كتابة موضعي محمول. لا حاجة إلى unsafe جديد لمجرد الكتابة عند offset؛ إذا استُخدمت واجهات منصة تعزل في crate مع مراجعة مستقلة. لا يرسل callbacks إلى الواجهة أثناء احتجاز موارد الكاتب، ولا يسقط future باعتباره إيقافًا لعملية قرص.

عند خطأ كتابة أو مزامنة أو إقرار ملتبس يتسمم handle ويغلق؛ إعادة الفتح هي وسيلة معرفة ما اعتمد. خطأ شبكة عابر لنطاق واحد لا يلغي نطاقات أخرى سليمة أو يعتمد ناقصه؛ يعاد فقط النطاق غير المكتمل بعد حد المحاولات والانتظار. تغير ETag أو خطأ هوية يوقف الجيل كله. فشل التخزين يوقف جميع العوامل لمنع تراكم buffers.

## المخطط المقترح والاستعادة

مخطط نقل جديد v4، مستقل عن نسخة مخزن الطابور. جدول job يحفظ الهوية، layout، generation، الحجم، حالة التحقق/النشر، والبصمة النهائية إن حُسبت. جدول ranges يحفظ حدود وحدات الاستعادة المعتمدة وبصمتها وcommit sequence. جدول/قيود إضافية تمنع سجلات خارج الحجم أو مكررة؛ يتحقق قارئ المخطط أيضًا من التداخل والتغطية، ولا يعتمد على CHECK محلي لا يرى الصفوف الأخرى.

حالة InFlight لا تستعاد كإنجاز. عند فتح المخزن تتحقق بصمات النطاقات committed بقراءة محدودة الذاكرة؛ إعادة التحقق تدريجية ممكنة لاحقًا، لكن لا يسمح بالكتابة أو النشر اعتمادًا على نطاق لم يتحقق بعد. جزء فاسد يحدد بالضبط ويُطلب قرار إعادة تنزيله ضمن سياسة التعافي؛ النسخة الأولى تستطيع الفشل المغلق دون إخفاء فساد. لا يقص الملف عند أول فجوة. البيانات في النطاقات غير المعتمدة لا تمنح أي تقدم، ويعيد الكاتب الكتابة عليها عند حجزها من جديد.

الإقرار الدائم يعتمد على الترتيب: كتابة البيانات → مزامنة الملف → معاملة اعتماد النطاقات → إقرار المتانة. انهيار قبل المعاملة قد يترك بايتات جيدة غير معتمدة يعاد تنزيلها، لكنه لا ينتج ثقة كاذبة. انهيار بعد commit وقبل الإقرار يصالح بإعادة فتح الخريطة؛ لا يعاد تنزيل الجزء لمجرد ضياع إقرار الذاكرة.

## ترحيل لا يعرّض النسخ القديمة للتقصير

1. يفتح migrator المخزن بقفل OS نفسه، دون بدء عوامل. يتحقق من نسخة المصدر والهوية والمرحلة وhash البادئة القديمة، ويوقف الترحيل عند أي فساد. مهمات النشر الجاري أو المكتملة تنهي دورة النسخة القديمة، ولا تحول إلى مخزن قابل للكتابة.
2. يدعم الترحيل الأول v2 معلوم الطول في Downloading فقط. v3 مجهول الطول غير المكتمل يبقى في المسار الحالي الرافض للاستكمال؛ لا يستنتج حجمًا منه. لا ترحيل صامت لكل ملف في الخلفية.
3. أثناء تحقق البادئة يحسب hashes لوحدات كاملة وبادئة الوحدة الأخيرة إن وجدت، بذاكرة محدودة. الجزء الأخير المستورد يمكن تمثيله كنطاق جزئي موثق؛ يحتاج استكمال بقية الوحدة إثبات هوية ونهاية سليمة قبل دمج اعتمادها. لا نسقط البايتات القديمة المحفوظة لتبسيط الخريطة.
4. ينشئ جداول v4 ويملأها ويغير version داخل **معاملة SQLite واحدة في state.sqlite نفسه**، بعد مزامنة البادئة. لا يعيد تسمية ملفي بيانات وسجل على افتراض ذرية مشتركة. لا يمدد payload ولا يكتب خارج البادئة قبل commit الترحيل.
5. الانهيار قبل commit يترك مخططًا قديمًا وبادئة لم تتغير؛ بعد commit يفتح v4. القارئ القديم يفحص version ويرفض v4 قبل تقصير payload، كما يفعل قارئ المخزن الحالي للنسخ غير المعروفة. يختبر هذا الشرط صراحةً ببرنامج قديم مثبت قبل اعتماد الترحيل.
6. إذا كانت نتيجة commit ملتبسة يغلق الكاتب ويفحص المخطط بإعادة الفتح تحت القفل. لا محاولة rollback تطبيقية تمس payload، ولا تعديل يدوي لرقم النسخة لاستعادة تشغيل البرنامج القديم.

هذا يحدد ذرية ترحيل metadata ضمن ضمانات SQLite والملف المتزامن؛ لا يثبت متانة power loss على Windows. مزامنة الدليل واستقرار النشر على المنصات الثلاثة تبقيان بوابة تأهيل مستقلة.

| إلغاء أثناء انتظار مساحة القناة/السرعة/القرص | لا orphan task، والقفل متاح بعد انتهاء shutdown، والحفظ المعلن يطابق الاستعادة |

| ترحيل v2 عند كل حد قبل وبعد commit | إما v2 صالح أو v4 صالح؛ لا فقد للبادئة؛ برنامج v2 يرفض v4 دون تغيير ملفه |
| اكتمال sparse file مع فجوة صفرية | لا نشر لمجرد وصول طول الملف إلى total؛ لا يمر إلا اتحاد نطاقات يغطي [0,total) |
| قياس 1 GiB و10 GiB على الأنظمة الثلاثة | تسجل الذاكرة وCPU والسرعة وعدد GET وbytes الزائدة وزمن shutdown والاستعادة، مع baseline أحادي وحالي، دون افتراض نسبة تحسن مسبقة |

تنفذ هذه الخطة على مراحل: عقود وخريطة مخزن واختبارات انهيار أولًا؛ الكاتب المحدود ثانيًا؛ منسق مستقل وprobe ثالثًا؛ ثم قياس وضبط التوازي. لا يستبدل المسار الحالي حتى تنجح اختبارات التكامل والترحيل ومراجعتا Engineering وSecurity مستقلتان.

### توضيح البذرة والنطاق الجزئي المستورد

وحدة الاستعادة 4 MiB ليست بالضرورة طلب HTTP واحدًا: أول بايت probe ثم [1,4 MiB) طلبان غير متداخلين داخل الوحدة الأولى. الكاتب يتتبع تغطية الطلبات التي ثبتت نهايتها، ولا يعتمد الوحدة كاملة لمجرد وصول البذرة. يمكن أن تبقى البذرة غير متينة حتى اكتمال الوحدة؛ خسارة بايت probe واحد بعد انهيار مقبولة ولا تُعرض كتقدم دائم. أما بادئة وحدة مستوردة من v2 فهي بيانات متينة أصلًا، تحفظ كسجل جزئي ببصمتها ولا يعاد طلبها. عند اكتمال بقيتها يحسب الكاتب hash الوحدة كاملة بقراءة محدودة ويستبدل السجل الجزئي بالسجل الكامل داخل معاملة الاعتماد، دون إعادة كتابة البادئة. بهذه القاعدة لا نخلط «تقسيم الطلبات» مع «حجم وحدات الاستعادة» ولا نفقد ضمانات النسخة القديمة أثناء الترحيل.
