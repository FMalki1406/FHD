# إدارة المهام داخل المحرك

الحالة: وحدة داخلية لإدارة مهام متعددة ضمن عملية واحدة؛ ليست بعد طابورًا دائمًا أو API للمتصفح. المحرك يبقى مسؤولًا عن حالة التنزيل، والواجهة المستقبلية تعرض snapshots وتطلب الأوامر.

## العقد

Manager::start يحدد حد التنزيلات النشطة وعدد المهام المحفوظة في الذاكرة. enqueue يقبل الخيارات ويعيد JobId، مع ترتيب FIFO. pause يرسل إشارة ثم ينتظر نتيجة العامل؛ لا يحرر خانة التزامن قبل تحرير التخزين. resume يعيد المهمة الموقوفة أو الفاشلة إلى آخر الطابور، ولا يغير الرابط أو الوجهة تلقائيًا. المكتمل لا يبدأ مجددًا بنفس الأمر.

shutdown يوقف قبول العمل ويطلب توقف التنزيلات ثم ينتظرها؛ لا يقتل عوامل الكتابة. إسقاط Manager وحده يطلب إغلاقًا غير متزامنًا طالما runtime حي؛ على التطبيق انتظار shutdown قبل إغلاق runtime أو العملية. إذا سبق النشر النهائي الإيقاف، تكون النتيجة Completed؛ لا نصف ملفًا منشورًا بأنه متوقف مؤقتًا.

الحالات: Queued وRunning وPausing وPaused وCompleted وFailed بفئة خطأ منقحة. حالة Failed عند تعذر حفظ checkpoint تبقى فشلًا ولا تتحول إلى Paused ناجحة. snapshots تعرض هوية المهمة والحالة والبايتات المحفوظة، بلا روابط أو مسارات أو رؤوس. تقدم checkpoint لا يمثل سرعة الشبكة اللحظية؛ الواجهة المستقبلية تحتاج قياسًا منفصلًا.

## الحدود

- الذاكرة تحتفظ بالخيارات اللازمة للتشغيل؛ لا يُحفظ طابور المهام أو الروابط على القرص. بيانات كل تنزيل المكتوبة تبقى في transfer-store؛ بعد إعادة تشغيل البرنامج يتطلب استئنافها تمرير الخيارات مجددًا.
- الحد شامل للمهام المكتملة والفاشلة؛ الإزالة والأرشفة وسياسة الاحتفاظ لاحقة. لا واجهة إنتاجية تعتمد هذا الحد دون رحلة لإدارة التاريخ.
- حد التزامن عالمي ومعه حد لكل أصل وأولويات كما في القسم المضاف أدناه؛ الجدولة الزمنية والنقل المتوازي لأجزاء ملف واحد لاحقان.
- رفض الوجهات المكررة يقلل تنازع المهمة؛ قفل Store يظل صاحب حماية الملكية الفعلية. اختلاف aliases أو تبديل المسارات من برنامج بنفس المستخدم ليس محميًا بالكامل.
- لا retry تلقائي أو حذف تلقائي أو استبدال عند خطأ. الإيقاف قبل إنشاء بيانات قد يترك مجلدًا غير موجود؛ هذا سلوك طبيعي.
- لا مصادقة IPC أو تفويض تجاري في هذه الوحدة. هي لمتصل محلي موثوق، ولا يجوز تعريض enqueue لصفحة ويب مباشرة.

مراجعة مستقلة واختبارات شبكة فعلية مطلوبة قبل اعتماد الدفعة؛ النتيجة المرجعية في [سجل التنفيذ](execution-status.md) و[مراجعة مدير المهام](task-manager-review.md).

حدود الموارد الحالية: 1 إلى 32 تنزيلًا نشطًا، وحتى 1024 مهمة إجمالية، وقناة أوامر بسعة 64. الحد النشط لا يتجاوز حد المهام. خيارات المهمة محدودة قبل دخول القناة؛ المصدر المحلي موثوق. قبول المسار يفحص القرص عبر عامل blocking وقد يؤخر الأوامر على filesystem بطيء؛ لا وعد زمن استجابة لهذا المسار بعد.

عودة shutdown بنجاح تعني اكتمال انتظار العوامل، ولا تعني نجاح كل checkpoint؛ على المتصل الاحتفاظ باشتراك snapshots وقراءة الحالات النهائية. pause يعيد خطأ إذا فشل العامل أثناء الإيقاف، مع سبب مفصل منقح في الحالة. إرسال أمر ثم توقف المتصل عن انتظار الرد لا يلغي الأمر الذي قُبل؛ واجهة التطبيق تحتاج مراعاة ذلك.

## أولوية وحدود لكل أصل

أضيف start_with_limits وحد للتزامن لكل أصل، مع enqueue_with_priority وset_priority للمهام غير الجارية. start السابق يحافظ على سلوكه ويضبط حد الأصل مساويًا للعالمي. راجع [سياسة الجدولة](scheduling-policy.md) لتعريف الأصل والأولوية الصارمة وحدود الإنصاف؛ لا يضيف هذا حفظ الطابور أو حد السرعة.
