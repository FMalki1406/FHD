# التوجه التقني

التاريخ: 2026-09-21. الحالة: توصيات قابلة للتعديل بعد إثبات الجدوى. لا توجد نتائج أداء مقاسة أو حزمة تقنية نهائية معتمدة.

تحديث تنفيذ: اعتمد Rust 1.98.1 لأساس قواعد النطاقات والحالات وسياسة الاستكمال، وأنشئت وحدتان بلا تبعيات خارجية. نجح 19 اختبارًا وفحصا التنسيق وClippy على Windows. هذا لا يحسم Tokio أو مكتبة HTTP أو SQLite أو Tauri ولا يثبت الأداء أو دعم بقية المنصات. [التفاصيل](development.md).

## قرارات وتوصيات

| المجال | التوصية | السبب وشرط تثبيت القرار |
| --- | --- | --- |
| محرك التنزيل | إبقاء Rust وTokio مرشحين أساسيين | ملاءمة الفصل عن الواجهة والتحكم في التزامن؛ إثبات الاستكمال والكتابة الآمنة أولًا |
| الواجهة | تقييم Tauri 2 مع React وTypeScript | مناسب للتصور الحالي؛ يثبت بعد قياس الاستهلاك وإتاحة الوصول وRTL على الأنظمة الثلاثة |
| بدائل الواجهة | مقارنة محدودة مع Electron وQt عند فشل شروط Tauri | لا نبدل التقنية دون أثر مقاس على الجودة والصيانة والتوزيع |
| التخزين المحلي | SQLite مع مالك كتابة واضح | معاملات محلية واستعادة قابلة للاختبار؛ المعاملة لا تضمن بمفردها أن بايتات الملف وصلت إلى القرص |
| امتداد المتصفح | منطق TypeScript مشترك مع طبقات توافق منفصلة | اختبار Chrome وEdge وFirefox فعليًا، والتحقق من Brave قبل ادعاء دعمه |
| الاتصال المحلي | Native Messaging ثم قناة محلية مقيدة بالمستخدم | بروتوكول بإصدارات، تحقق من الرسائل والمرسل وحدود الحجم، دون منفذ عام غير موثق |
| الخدمات الخلفية | تطبيق واحد بوحدات داخلية، مع PostgreSQL عند الحاجة | تجنب تكلفة الخدمات المصغرة المبكرة؛ لغة الخادم تحدد وفق الفريق والتكاملات |
| HTTP/3 | تجربة أداء منفصلة قبل تفعيله افتراضيًا | لا نفترض أن حداثة البروتوكول تعني تحسنًا لكل تنزيل |
| الوسائط | وحدة معزولة مع مهام دمج محدودة الصلاحيات | تبقى أخطاء المعالجة منفصلة عن التنزيلات؛ التوزيع والتبعيات يحتاجان مراجعة |

Tauri يستخدم WebView مختلفًا بحسب النظام؛ لذلك حجم الحزمة وحده لا يثبت انخفاض الذاكرة أو اتساق السلوك. المصدر: [Tauri Process Model](https://v2.tauri.app/concept/process-model/).

## تعديل مهم على المعمارية المقترحة

أوصي بتقييم عملية محرك مستقلة على مستوى المستخدم، لا خدمة بصلاحيات مدير. تبقى الواجهة عميلًا لها، ويستطيع تعطل الواجهة ألا يوقف التنزيل. تكلفة ذلك إدارة دورة الحياة والاتصال والتحديث والتوافق بين الإصدارات؛ لا نعتمده قبل اختبار هذه الحالات. البديل محرك داخل العملية الرئيسية مع تعافٍ بعد التعطل.

إغلاق النافذة، الخروج الكامل، تسجيل الخروج من النظام، وإيقاف الجهاز حالات مختلفة يجب أن يفهم المستخدم أثر كل منها. لا نعد بالتنزيل أثناء نوم الجهاز أو إيقافه.

## ثوابت السلامة في التصميم

1. حالة التنزيل المرجعية في المحرك، والواجهة تعرض لقطات محدودة التردد.
2. تخزين نطاقات مؤكدة بعد ضمان كتابة بياناتها وفق سياسة المتانة؛ الاستعادة تعيد فحص الملف والحالة ولا تثق بعداد تقدم منفرد.
3. التحقق من هوية المورد وصحة استجابة Range؛ لا دمج لنسختين اعتمادًا على الاسم والحجم وحدهما. ضعف أو غياب أدوات التحقق يستلزم مسارًا محافظًا.
4. التحقق من الملف المؤقت قبل إظهاره كمكتمل، ثم نشره بأمان، وتسجيل الاكتمال بعد نجاح العملية. الاستعادة تعالج الانقطاع بين هذه المراحل.
5. لا نفترض أن النقل بين قرصين عملية ذرية؛ له مسار نسخ وتحقق واستعادة مستقل.
6. Cookies وAuthorization أسرار؛ تُقيد بالمصدر والاستخدام، ولا تنتقل إلى وجهة تحويل مختلفة تلقائيًا أو إلى سجل التشخيص.
7. الخادم التجاري لا يحمل بايتات تنزيل المستخدم ولا يحتاج سجل تصفحه لتفعيل الرخصة.

مرجع دلالات التحقق والاستكمال: [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html). ما سبق توصيات تصميم مستندة إلى الدلالات، وليس ضمانًا يقدمه البروتوكول لكل خادم.

## إثبات جدوى تكامل المتصفح

لا نفترض إمكانية نسخ كل طلب من المتصفح. تُختبر التنزيلات العادية، التحويلات، الجلسات، الروابط المؤقتة، POST، وblob كل على حدة. الحالات غير المدعومة تظل في المتصفح مع تفسير واضح. إعادة إرسال طلب ذي أثر جانبي ليست إجراءً تلقائيًا.

تُختبر دورة الحياة عند إغلاق المتصفح والتطبيق، الرسائل المكررة، فشل الحفظ، اختلاف إصدار الإضافة، ومحاولة انتحال المرسل. Native Messaging وسيلة اتصال وليست بديلًا عن تحقق التطبيق.

المراجع: [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)، [Chrome Downloads API](https://developer.chrome.com/docs/extensions/reference/api/downloads). يلزم استكمال مراجعة Firefox وقيود المتاجر قبل الاعتماد النهائي.
