# مراجعة مستقلة لتوسعة المحرك

التاريخ: 2026-09-21. النطاق: سياسات الطلب والجلسات والتحويلات، نقل دون طول معلن، إدارة الملفات، تجديد روابط التنزيل، وحد إدخال المتصفح. المراجع: وكيل Security/Engineering مستقل عن منفذي هذه الدفعة. الحالة: روجعت مسودات التنفيذ وأعيد فحص إصلاحات السلامة؛ قبول الاختبارات النهائي مرجعه سجل التنفيذ. لا يمثل هذا المستند دليل تشغيل اختبارات بحد ذاته.

## ثوابت القبول

- تبقى Cookies وAuthorization مقيدتين بالأصل المصرح، ولا تتسربان عبر تحويل إلى أصل آخر أو في أخطاء وسجلات أو حفظ واضح للطابور. لا تعطيل TLS ولا خفض HTTPS إلى HTTP بسبب سماح عام بـHTTP.
- سياسة الوجهات والصلاحيات تصدر من caller محلي موثوق؛ لا تمنح صفحة أو رسالة متصفح نفسها إذن شبكة خاصة أو توسيع تحويلات أو كتابة مسار. نوع Rust وحده لا يثبت أصل الرسالة.
- النقل مجهول الطول يحتاج نهاية framing صحيحة وحدًا أقصى للأحجام وإيقافًا آمنًا. لا يستكمل سجلًا جزئيًا بافتراض طول أو هوية غير مثبتين، ولا ينشر مجرد وصول socket إلى نهاية غير قابلة للتمييز عن قطع الاتصال.
- تجديد URL ليس إثباتًا أن المورد نفسه. ETag مع الحجم ليس معرفًا عالميًا عبر موارد أو أصول مختلفة. لا دمج جزئي بلا سياسة موثقة وتحقق ملائم؛ البصمة الموثوقة لكامل الناتج تمنع نشر ملف مختلط وإن لم تمنع تنزيله.
- إدارة الملفات لا تستبدل ملفًا موجودًا ولا تحذف مجلدًا كاملًا بناء على input. تفصل الإلغاء وإزالة سجل المهمة وحذف الناتج؛ تملك قفل المهمة وتتحقق من الاسم والوجهة والملكية والحالة قبل mutation.
- النشر والنقل بين أقراص مختلفة لهما خطوات حفظ واستعادة؛ لا تسمية نسخ ثم حذف عملية ذرية. ملفات تعديل المستخدم تصان.

## أدلة مطلوبة

1. خادمان مختلفان يثبتان عدم عبور أسرار جلسة، واختبارات downgrade وتجاوز redirect budget ورؤوس ممنوعة وأخطاء منقحة.
2. framing مجهول الطول مكتمل ومقطوع، صفر بايت، حد الحجم، إلغاء وفشل حفظ؛ لا نشر عند الفشل واستعادة ذات سياسة واضحة.
3. تجديد رابط إلى ملف مختلف يحمل ETag وحجمًا متماثلين، وتبديل أصل أو مسار، وتكرار/انقطاع خطوات التجديد؛ لا نشر مختلط أو فقد checkpoint.
4. رفض تعارض اسم أو رابط رمزي أو ملف أجنبي عند إدارة المخرجات، وصيانة تعديل المستخدم، وقفل بين ناقل وأمر ملف.
5. إدخال متصفح مشوه أو مكرر أو غير موثوق، وقيود طول وحجم/عدد، وعدم إرسال نجاح handoff قبل قبول محفوظ حيث يدّعى دعمه.

تسجل نتائج التشغيل الفعلية مركزيًا في [حالة التنفيذ](execution-status.md). لا يشغل هذا المراجع Cargo بالتوازي مع المنفذين. حدود filesystem الحالية تفترض مجلدًا خاصًا موثوقًا ولا تضمن مقاومة تبديل المسارات المتزامن من مهاجم يملك حساب المستخدم.

## ملاحظات مبكرة للمنفذين

أرسلت قبل التنفيذ تنبيهًا بأن ETag scoped للمورد ولا يصح اعتباره هوية عالمية لتجديد الرابط، وأن typed browser input لا ينشئ هوية/صلاحية مرسل موثوقة، وأن حذف الملفات يحتاج ملكية وقفلًا ومنع استبدال. ستضاف نتيجة مراجعة الملفات الفعلية بعد اكتمالها.

## مراجعة المسودات

- راجعت RequestPolicy وتكامل الناقل المتوازي: الرؤوس محدودة إلى Authorization وCookie، حقن التحكم مرفوض، وDebug منقح. التحويل يفحص كل خطوة، والرؤوس الحساسة لا تنتقل إلى الأصل الآخر، والتخفيض من HTTPS مرفوض. اختبارات HTTP مكتوبة للتحقق الفعلي من ذلك؛ التشغيل مسؤولية الوكيل الرئيسي.
- حد Cookie الخام وثق في request-compatibility.md: صلاحية أصل كاملة وليست دلالات Path/SameSite/Secure/expiry للمتصفح. لا يصلح هذا وحده لادعاء تكامل جلسات متصفح مكتمل.
- راجعت unknown.rs والتخزين: يقبل HTTP/1.1 chunked أو framing HTTP/2 دون طول، ويرفض close-delimited. يحد البايتات قبل الكتابة، ويحفظ الحجم الفعلي وعلامة الإكمال بمعاملة بعد checkpoint. استعادة سجل غير مكتمل لا تلحق به بيانات وتعيد ResumeUnsupported. فرع HTTP/2 يحتاج دليله المنفصل قبل وصفه بأنه اختبر.
- أرسلت ملاحظة مانعة على مسودة تصدير الملف: مقارنة الحجم فقط بعد النسخ لا تكشف تعديلًا بنفس الحجم أثناء النسخ. المطلوب مقارنة بصمة النسخة ببصمة السجل المعتمدة قبل النشر. وطُلب تقييد محاولات الاسم المؤقت وبيان متانة ربط الوجهة.
- أرسلت ملاحظة مانعة على مسودة refresh_from: مجرد Some في API عام لا يجوز أن يعطل تطابق الرابط النهائي بلا شروط داخل الناقل؛ يجب فرض هوية/بصمة موثوقة في download_controlled نفسه، بما يغطي تجاوز wrapper بطريق الخطأ.
- روجع ربط GetDiskFreeSpaceExW: نص UTF-16 منتهٍ، مخرج u64 حي، لا قراءة عند فشل الاستدعاء؛ القيمة للمستخدم ويمكن أن تتأثر بالحصص، وهي فحص استرشادي لا حجز مساحة. [Microsoft الرسمي](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdiskfreespaceexw). مسار Unix يحتاج بناء واختبار منصته مستقلًا.

## إعادة فحص الإصلاحات

- أضيفت مقارنة SHA-256 لبايتات التصدير مع بصمة السجل الذي أعيد التحقق منه، ومقارنة الحجم قبل hard_link. يحافظ التصدير على المصدر، ويستخدم create_new وno-replace وحدًا 1000 لمحاولات اسم الملف المؤقت. أضيفت مزامنة دليل الوجهة على Unix؛ لا دليل فصل طاقة Windows أو ملف تخصيص export دائم في هذه الدفعة. قد تبقى نسخة مؤقتة بعد قتل العملية، وقد تكون الوجهة نشرت قبل خطأ مزامنة؛ لا تعاد المحاولة بافتراض أن أي خطأ يعني عدم وجودها.
- فرض الناقل expected_sha256 عند أي refresh_from، وتظل مساواة البصمة المتوقعة بهوية التخزين شرطًا. يرفض manager تغيير أصل أو مسار المورد، ويسمح query جديدًا فقط. لا يعد ذلك برهان هوية query؛ البصمة الموثوقة تمنع نشر خليط. لا بصمة موثوقة يعني إعادة بدء صريحة بمهمة جديدة مع إبقاء القديمة.
- اكتشفت المراجعة أن إبقاء refresh_from لأول رابط كان يكسر التجديد الثاني بعد حفظ رابط جديد. عولج ذلك بمصالحة الهوية من Store تحت القفل قبل حفظ تحديث خيارات المهمة. يلزم اختبار تجديدين يفصل بينهما تنزيل جزئي.
- إزالة المهمة forget تمس السجل فقط ولا تحذف الملفات؛ تحفظ لقطة v2 آخر معرف خصص لمنع إعادة استخدام JobId بعد إزالة المهام. قارئ v1 يستعيد الحد الأقصى الموجود وسياسة طلب فارغة. لا يفترض القارئ أن بيانات الاعتماد موجودة في سجلات v1.
- Inbox محدود الحجم والعمر، ولا يمنح طلب URL سلطة رأس أو وجهة ملفات أو HTTP أو تحويلات. approve يتطلب استدعاء محليًا موثوقًا. ما زال in-process، دون مصادقة متصفح أو سياسة DNS/عناوين خاصة أو إثبات تسليم exactly-once دائم. نجاح enqueue يكون متينًا فقط مع Manager دائم؛ لا ينبغي إلغاء تنزيل المتصفح بناء عليه قبل إكمال بروتوكول التسليم الحقيقي.
- unsafe محصور في platform-files للاستعلام الأصلي. على Unix يقرأ statvfs بعد نتيجة نجاح فقط، ويحسب المساحة بـu128 ثم يحول بتحقق إلى u64؛ يحتاج بناء المنصة، ولا يثبت نجاح Windows صحة ABI والتنفيذ هناك.

## حدود ومتابعة

انتظار فتح Store داخل مسار refresh يعيد فحص الملف وقد يستغرق وقتًا لملفات كبيرة، ويؤخر معالجة أوامر manager الأخرى رغم أن القراءة داخل spawn_blocking. يلزم قياس ذلك أو إخراج المصالحة من actor قبل وعد استجابة واجهة أو إلغاء سريع أثناء التجديد. لا يوجد listener خارجي في النطاق الحالي، ولا حماية مكتملة من إعادة ربط DNS، ولا مخزن Cookie بدلالات متصفح، ولا تأهيل للأنظمة الثلاثة.

لا ملاحظة سلامة بيانات مانعة متبقية في الشفرة التي أعيدت مراجعتها بعد الإصلاحات المذكورة. هذا حكم محدود بمراجعة الشفرة، مع بقاء اختبارات الدفعة وقيود التشغيل أعلاه شرطًا مستقلًا؛ ليس إقرار جاهزية enterprise أو إطلاق عام.

## مراجعة الإضافات الأخيرة

فحص المساحة الجديد يعمل داخل spawn_blocking ويضيف احتياطًا ثابتًا قدره MiB واحد، مع checked_add. للملف معلوم الحجم يفحص البايتات المتبقية عند الاستكمال أو الحجم كاملًا قبل إنشاء المخزن؛ للمجهول يفحص الاحتياط فقط ويترك أخطاء القرص الفعلية لمسار الحفظ الآمن. لا يعد ذلك حجزًا لمساحة بين تنزيلات متزامنة. InsufficientSpace ليس ضمن أخطاء إعادة المحاولة الآلية.

كشفت إعادة الفحص عن تمرير مسار نسبي خام في فحص مساحة الاستكمال رغم أن فحص الوجهة يقبل المطلق فقط. عولج ذلك بتطبيع مسار الاستكمال إلى مطلق قبل الفحص، وأضيف اختبار executable لانقطاع ثم استكمال باستخدام دليل نسبي. روجع الإصلاح في الشفرة؛ نتيجة تشغيل اختبار CLI تسجل مركزيًا عند اكتماله. لا ملاحظة شفرة معلقة على فحص المساحة بعد الإصلاح.

روجع تعريف engine.yml: صلاحية قراءة فقط، لا أسرار إصدار أو توقيع أو نشر، مراجع Actions كاملة، وعدم حفظ بيانات اعتماد checkout، ولا interpolation من نص PR في أوامر shell. لا مانع أمني ظاهر ضمن النطاق. مصفوفة الأنظمة معرفة وليست دليل نجاح حتى تشغيلها؛ حمل 64 MiB الاختياري ليس تأهيل حمل طويل أو ملفات متعددة GiB.

## نتائج التنفيذ المركزي

سجل الوكيل الرئيسي نجاح 120 اختبار Rust (بما فيها تجربة 64MiB الاختيارية)، و18 تجربة executable، و21 للمختبر، و1 TLS على Windows. نجح اختبار الاستكمال النسبي المضاف بعد إصلاح preflight، ونجحت اختبارات رفض المحتوى المزور رغم ETag وطول متساويين. البناء والتنسيق وClippy لجميع targets بلا تحذيرات. هذه النتائج تغطي النطاق الداخلي الموثق؛ لا تغلق الحدود التشغيلية أعلاه.
