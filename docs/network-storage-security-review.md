# مراجعة أمان النقل والتخزين

التاريخ: 2026-09-21. المراجع: وكيل Security مستقل عن التنفيذ. هذه مراجعة تصميم وتبعيات أولية؛ يتبعها فحص الكود والأدلة قبل وصف أي ضابط بأنه منفذ. لا تشمل الترخيص أو الدفع اللذين يبقيان ضمن تصميم مستقل.

## التبعيات المرشحة ومصدر الاختيار

تحقق المراجع من صفحات الإصدارات الرسمية المنشورة؛ تثبيت الإصدار والـlockfile لا يعني خلو التبعيات من الثغرات. القرار النهائي مرتبط بملفات Cargo الفعلية ونجاح البناء.

| التبعية | الإصدار المتحقق منه | الميزات الدنيا المقترحة | الترخيص والملاحظة |
| --- | --- | --- | --- |
| reqwest | 0.13.5 | إيقاف default-features؛ rustls؛ لا cookies أو JSON أو ضغط أو system-proxy | MIT أو Apache-2.0؛ مزود TLS وتبعياته تحتاج جردًا مستقلًا |
| Tokio | الأحدث 1.53.1؛ المرشح المثبت 1.51.4 من فرع LTS | rt، macros، time، sync؛ net/io-util/fs عند الاستخدام الفعلي فقط | MIT؛ فرع 1.51 مدعوم حتى مارس 2027 وفق صفحة المشروع |
| rusqlite | 0.40.2 | إيقاف default-features؛ bundled، بلا load_extension أو SQLCipher | MIT؛ SQLite المضمّن له شروطه المنفصلة؛ لا اعتماد على DLL محلية عشوائية |
| sha2 | 0.11.0 | الميزات الافتراضية الدنيا للبصمات | MIT أو Apache-2.0؛ بصمة سلامة محلية، وليست توقيع مصدر الملف |

المصادر: [reqwest](https://docs.rs/crate/reqwest/0.13.5)، [خيارات HTTP](https://docs.rs/reqwest/0.13.5/reqwest/struct.ClientBuilder.html)، [Tokio والإصدارات المدعومة](https://docs.rs/crate/tokio/1.53.1)، [rusqlite](https://github.com/rusqlite/rusqlite)، [ميزات rusqlite](https://docs.rs/crate/rusqlite/0.40.2/features)، [sha2](https://docs.rs/sha2/0.11.0/sha2/).

يلزم تثبيت المباشرة بصيغة =version وحفظ Cargo.lock، وجرد تراخيص transitives ونتيجة فحص [RustSec](https://rustsec.org/) قبل إصدار تجاري. لم ينفذ هذا الملف فحص advisory كاملًا ولا يدعي ذلك. عند اختلاف توفر نسخة في registry عن الصفحة الرسمية يُوثق الفرق ولا يُخفى بإعلان نجاح بناء.

فُحص Cargo.lock بعد حله: reqwest 0.13.5 وTokio 1.51.4 وrusqlite 0.40.2 وsha2 0.11.0، مع aws-lc-sys 0.45.0 وrustls-webpki 0.103.15. فحص يدوي محدود للإشعارات أثبت أن هذه النسخ تتجاوز حدود الإصلاح في [RUSTSEC-2026-0049](https://rustsec.org/advisories/RUSTSEC-2026-0049.html) و[RUSTSEC-2026-0048](https://rustsec.org/advisories/RUSTSEC-2026-0048.html) و[RUSTSEC-2025-0023](https://rustsec.org/advisories/RUSTSEC-2025-0023.html) و[RUSTSEC-2021-0100](https://rustsec.org/advisories/RUSTSEC-2021-0100.html). هذه عينة محددة وليست نتيجة cargo audit أو تدقيقًا شاملًا للتبعيات.

## حدود الثقة المعتمدة لهذه الخطوة

المحرك مكتبة محلية يستدعيها كود موثوق باختيار تنزيل صريح. ليس خادمًا عامًا أو مستقبلًا لأوامر صفحات ويب. لا يمنع كل LAN تلقائيًا لأن تنزيل ملفات intranet مشروع. قبل توصيله بامتداد أو IPC، يلزم قرار أصل الطلب وصلاحيات المستخدم وسياسة عناوين خاصة وloopback وlink-local وفحص DNS والعنوان المتصل وكل redirect؛ فحص اسم المضيف وحده لا يمنع DNS rebinding.

تعطيل proxy التلقائي هنا يجعل الاختبارات والحدود قابلة للتفسير، لكنه لا يحقق دعم شبكات المؤسسات التي تحتاج proxy وشهادات خاصة؛ هذا تكامل لاحق صريح. لا تعطيل للتحقق من شهادات TLS كحل توافق.

## شروط قبول التنفيذ

1. رفض البروتوكولات غير HTTP(S) وuserinfo، وتحديد حجم URL وعدد التحويلات. كل redirect يعاد التحقق منه؛ لا downgrade من HTTPS إلى HTTP. وضع مختبر HTTP محلي واضح ومنفصل عن افتراضات الويب.
2. عدم إرسال Authorization أو Cookie أو Referer ضمن هذه الخطوة، وتعطيل redirects وproxy الافتراضيين. عدم إدخال URL أو query أو ETag أو أخطاء reqwest الخام في Debug أو السجلات.
3. طلب identity وعدم فك الضغط آليًا؛ حفظ تكرار الرؤوس للسياسة، وربط الاستكمال بالرابط النهائي وETag قوي وحجم التمثيل. اختلافها يوقف الكتابة ولا يبدأ ملفًا جديدًا فوق الجزء القديم ضمنيًا.
4. سقف bytes وزمن الاتصال وانتظار بيانات وحدود buffering؛ اختبار جسم ناقص/زائد وانقطاع وإلغاء. عدم إعلان الاكتمال بناءً على الرأس وحده.
5. إنشاء حصري للملفات؛ لا مسار من اسم شبكة، ولا استبدال ملف موجود عند النشر. توثيق حدود symlink/reparse/سباقات تعديل الوجهة قبل توصيل وجهة يحددها طرف غير موثوق.
6. مزامنة بيانات part قبل تسجيل تقدم متين في SQLite. عند الاستعادة، تحقق بصمة الجزء والهوية والحجم؛ البايتات التي لم تلتزم لا تصبح تقدمًا موثوقًا.
7. عدم اعتبار WAL checkpoint دليل مزامنة الملف؛ تفعيل المتانة المطلوبة والتحقق من الإعدادات. [SQLite synchronous](https://sqlite.org/pragma.html#pragma_synchronous).
8. حجز كاتب واحد، ومنع فتح schema أحدث أو إعادة تهيئة قاعدة تالفة تلقائيًا. نشر الملف مع intent يسمح بالتعافي من توقف العملية بين النشر وتسجيل الاكتمال.

## المخاطر وبوابات الإطلاق المتبقية

- دعم الأنظمة والـfilesystems وإثبات مقاومة سباقات الروابط الرمزية، واختبارات فصل الطاقة وفشل القرص، تحتاج أدلة خاصة بكل منصة. نجاح Windows الوظيفي لا يثبتها.
- روابط الاستكمال المخزنة قد تحتوي أسرارًا في query. لا تدخل log أو حزمة دعم؛ حماية التخزين/ACL وحساب المستخدم وتشفير أسرار النظام تحتاج حسمًا عند دمج التطبيق. قاعدة SQLite نفسها ليست تشفيرًا.
- SHA-256 يكتشف تغيير الجزء المحلي مقارنة بالسجل؛ لا يحمي من مهاجم قادر على تعديل الملف والبصمة معًا ولا يثبت ناشر ملف منزل.
- قبول URL بإجراء محلي موثوق لا يبرر توصيل API غير موثوق لاحقًا دون مراجعة جديدة.

## نتيجة مراجعة الكود

راجع الوكيل transfer-store بعد كتابته وقبل أول تشغيل اختبارات. كُشفت وعولجت نصيًا ثلاث ملاحظات:

| الملاحظة | الإصلاح الذي أعيد فحصه | الدليل المطلوب |
| --- | --- | --- |
| إعادة فتح ملف منشور تقص البايتات التي أضافها المستخدم بسبب hard link مع part | يمنع تعديل الطول عندما تجاوزت المهمة مرحلة التنزيل، ويرفض الحالة دون تغيير الملف | اختبار published_file_user_edits_are_preserved_on_reopen مكتوب؛ تشغيله ينتظر اكتمال البناء |
| النشر يتحقق من بصمة prefix فقط وقد ينشر tail إضافيًا | publish يتحقق من الحجم الدقيق ويعيد البصمة قبل الربط | اختبار externally_appended_tail_cannot_be_published مكتوب؛ نجح ضمن الاختبارات النهائية المسجلة في execution-status.md |
| فتح ملفات خاصة مثل FIFO قد يعلق الاستعادة | فحص regular files للسجل والقفل والجزء والنهائي، ورفض special files والروابط | مراجعة الكود منفذة؛ اختبار الأنظمة الأخرى لم ينفذ |

التخزين يستخدم journal_mode=DELETE وsynchronous=FULL؛ هذا اختيار أبسط لهذه الوحدة وليس تنفيذ WAL. يستخدم hard link حصريًا داخل نفس مجلد المهمة للنشر، ويبقي part. لا يعمل مع filesystem لا يدعم hard links. مقارنة hash عند استعادة intent تتحقق من المحتوى ولا تثبت ملكية ملف مطابق سبق أن أنشأه طرف آخر؛ لا يُستبدل الملف الموجود.

اكتملت المراجعة النصية المستقلة للوحدتين بعد الإصلاحات، وتبقى نتائج التشغيل مرتبطة بسجل التنفيذ. لا موافقة إصدار إنتاجي من هذه المراجعة. مزامنة الدليل في Windows غير منفذة؛ لا ادعاء ضمان نشر الملف عند فصل الطاقة. فحص المسار ثم فتحه لا يمنع سباق تبديله بواسطة برنامج يملك حساب المستخدم؛ الاستخدام الحالي مشروط بمجلد عمل يملكه التطبيق ولا يشاركه كاتب غير موثوق.

### فحص download-engine الأول

فُحص التنفيذ النصي: التحويلات يدوية بحد خمسة وتقتصر على نفس origin، مما يمنع downgrade أيضًا لكنه يقيد بعض CDN المشروعة. الأخطاء فئات منقحة، وidentity مطلوب، وربط final URL وETag قوي للاستكمال ظاهر في الكود. عدم وجود علامة انتهاء جسم صحيحة يرفض نشر prefix كامل، حتى إن كانت كل البايتات محفوظة؛ هذا فشل محافظ يحتاج رحلة استعادة لاحقة.

أرسلت الملاحظات التالية للمنفذين وأعيد فحص إصلاحاتها في الكود:

- Store::open ينشر intent قبل تحقق المحرك من URL وبصمة المهمة المطلوبة؛ فصل الاستعادة عن أثر النشر والتحقق أولًا.
- مقارنة output_name للمهمة المستعادة مع خيار الاستدعاء؛ لا تجاهل اسم مختلف.
- حد i64::MAX للحجم ليس حصة قرص عملية؛ إضافة حد ملف قابل للضبط والتحقق منه قبل الكتابة.
- رفض Content-Range في 200 عند البدء من صفر في مهمة موجودة، مثل سلوك المهمة الجديدة.
- إعادة فحص الإلغاء بعد فتح القرص وقبل النشر المباشر.

أصبح open لا ينشر، ويتحقق المنسق من URL والبصمة واسم الملف والحجم المسموح قبل finalize. أضيف max_download_bytes قابل للضبط، وفحص Content-Range في الحالتين، وفحص الإلغاء بعد فتح السجل وقبل الإكمال. طلبت اختبارات منع الانتكاس للحجم وتغيير اسم المهمة وربطها. لا ملاحظة أمان حرجة غير معالجة ضمن نطاق المكتبة المحلية الخاص المحدود بعد هذه الإعادة؛ حدود filesystem والـURLs المخزنة والسياسات قبل IPC تبقى بنود إصدار مفتوحة، وليست ضوابط منفذة.

## دليل الإغلاق الهندسي

نجح التحقق النهائي على Windows: 36 اختبار Rust و21 مختبر و13 تكامل. اختبارات ReadyToPublish تثبت رفض اختلاف الرابط والاسم وفقد قناة المالك دون نشر. عولج فحص الإلغاء بين قطع الكتابة ووثّق عدم إسقاط future ومرحلة النشر غير القابلة للمقاطعة. لا يغير نجاح هذه الاختبارات بوابات الإصدار المفتوحة المذكورة أعلاه.
