# حالة التنفيذ والأدلة

آخر تحديث للحالة: 2026-09-23. FHD اسم عمل وليس علامة تجارية معتمدة.

## ⛔ إصدار محظور — والثغرة ما زالت موجودة

**هذه ليست حالة «احتواء تقني مكتمل».** الحظر يمنع التوزيع؛ **العيب قائم في الكود** ولم يُصلَح.

### ما هو العيب

النشر يربط **اسمًا**، والتحقق يجري على **مقبض**. فبين إثبات البايتات وظهورها في الوجهة يمكن استبدال ما يدلّ عليه الاسم. أُثبت بالتجربة على ثلاث محاولات متتالية، وآخرها — التدريج داخل مجلد المحرك، وهو **ما على `main` الآن** — نافذته `O(حجم الملف)`، أي **أطول** من التي استبدلتها.

> **وإصلاح التعافي لا يعالج هذا.** هو يجعل الفشل قابلًا للرجوع منه، ولا يمنع استبدال الملف عند النشر. بندان مستقلان.

### ما الذي يحميه فعلًا اليوم

قائمة التحكم على مجلد الأجزاء: قياسًا برمز مقيَّد على Windows، حساب محلي آخر **لا يصل إلى الجزء إطلاقًا**. والطريق الوحيد الذي يلتفّ — إعادة توجيه سلف — يغلقه NTFS لا كودنا، **وهو باطل على Unix**.

### نطاق فحص التوزيع

**لا يُقال «لم يُوزَّع شيء» على إطلاقه.** ما فُحص، وكلٌّ على حدة (٢٠٢٦-٠٩-٢٤):

| القناة | النتيجة |
| --- | --- |
| إصدارات GitHub | صفر |
| وسوم | صفر |
| **مرفقات Actions** | صفر |
| حزم (container) | لا توجد |
| عمليات نشر (deployments) | صفر |
| GitHub Pages | غير مفعّل |
| خطوة رفع أو نشر في أي workflow | **لا توجد** — فحص نصّي لكامل `.github/` |

**وما لم يُفحص ولا يمكن فحصه:** المستودع **عام**، فالبناء من المصدر متاح لأي شخص. صفر فروع (forks) وقت الفحص، وهذا لا يمنع نسخًا لم تُسجَّل. **فالقول الدقيق: لا توجد ثنائيات موزَّعة عبر قنوات هذا المستودع.**

### حكم الاستعمال

**لا يُعتمد بناء من `main` للاستعمال الإنتاجي** حتى يُصلَح عقد النشر ([الوثيقة](publication-contract.md)). ولا يُوسَم ولا يُصدَر. مذكور في `README.md` و`development.md` عند تعليمات البناء والتشغيل، لا هنا وحده.

### التعطيل والتراجع — قُيِّما، والقرار عدم التراجع

| الخيار | الحكم |
| --- | --- |
| التراجع عن التدريج | **مرفوض.** يعيد المحاولة الثانية، **وفيها الثغرة نفسها**: الاسم النهائي يظهر قبل الإثبات، والإزالة عند الفشل قد تحذف وجهة مستبدَلة. والقاعدة: لا رجوع تلقائي إلى تنفيذ فيه العيب نفسه |
| تعطيل مسار النشر | **مرفوض.** تعطيل النشر تعطيل للمنتج |
| **حظر الإصدار + إصلاح التعافي + إغلاق العقد** | **المعتمد** |

**ولا تُمسّ بيانات المهام في أي خيار:** لا خطوة في هذا العمل تحذف ملفًا جزئيًا ولا سجلًا.

## الوضع الحالي

المرجع الموحد للحالة هو [سجل التطبيق](enterprise-implementation-status.md)، بلقطة الكود المحفوظ `bcbc04266d03af694d9c127e22c8b31bb25b0710`. هذه اللقطة لا تشمل تعديلات IPC/platform والبناء الجارية في مساحة العمل. تحديث الوثائق طابق المصدر وعقوده واختباراته ولم يُشغّل CI أو الاختبارات من جديد.

| المسار | الحالة الحالية |
| --- | --- |
| المحرك الجديد | fhd-engine يركب النقل والمنسق والمجدول وSQLite والملفات؛ تنزيل ونشر واستعادة، --continue وخدمة --serve وعميل --client |
| المتانة | نطاقات ببصمات بعد sync ومعاملة، نوايا نشر ومصالحة؛ النشر hard link بلا استبدال مع تحرير part لاحقًا، وليس rename أو fallback عبر الأقراص |
| التحكم | IPC محدود بإصدار؛ تحقق الطرف على Unix، وضوابط Windows في النسخة المرجعية غير مكتملة؛ لا تفويض مستقل حسب نوع العميل |
| المحرك القديم | fhd-transfer باقٍ بمساره ومديره وحفظ الطابور المشفر على Windows؛ وجود المحرك الجديد لا يعني استبداله |
| قبل الإطلاق | الواجهة والمتصفح والترخيص والموقع والتحديث والتوقيع والسياسات ومخزن أسرار النظام وتأهيل الأداء ما زالت غير مكتملة |
| التحقق | تعريف CI واختبارات فعلية موجودة؛ النتائج التاريخية أدناه مقيدة بمعرفات المصدر، وليست شهادة للنسخة الحالية أو التعديلات غير المحفوظة |

حدود إضافية: نية النشر الحالية لا تتضمن عقد هوية ملف المنصة الكامل، وتنظيف المهام المعروفة ليس جامعًا عامًا لكل الملفات اليتيمة. لا يثبت الاختبار المكتوب أو نجاح CI تحمل فصل الطاقة أو أهداف الأداء.

## سجل التطور والأدلة التاريخي

كل ما يلي سجل دفعات بترتيب إضافتها، بما فيه أوصاف «المنفذ» و«الخطوة التالية» وطلبات المساعدة وقتها. لا تُقرأ تلك الأوصاف كحالة راهنة؛ الحالة الراهنة أعلاه وفي سجل التطبيق. لا نحذف إخفاقًا سابقًا أو نحوله إلى نجاح بأثر رجعي.

### لقطة المحرك القديم في الدفعات الأولى

المشروع يستهدف إطلاقًا متكاملًا. نُفذ الآن أساس محرك Rust مع نقل فعلي ومتوازٍ، ومدير مهام يدعم حفظ الطابور المشفر على Windows وإعادة المحاولة وحدود السرعة الحية، وتخزين SQLite، واستعادة تنزيل من checkpoint، وتحقق SHA-256، ونشر الملف دون استبدال. هذه مرحلة هندسية داخلية؛ ليست تطبيق سطح مكتب جاهزًا للعملاء.

المستودع [FMalki1406/FHD](https://github.com/FMalki1406/FHD) مربوط بـorigin. نجح الرفع السابق بتحديد حساب FMalki1406 في إعداد مؤقت لأمر Git، دون كشف بيانات الاعتماد أو force. سجل Git هو مرجع الالتزامات.

### التحقق

البيئة: Windows x64، Rust 1.98.1، MSVC Build Tools 2019، Node.js 22.13.1. أدوات Rust محلية تحت .tools ومستثناة من Git، وكذلك target. التبعيات المباشرة مثبتة وCargo.lock محفوظ.

أوامر التحقق من الجذر موثقة في [بيئة التطوير](development.md) و[دليل المحرك](../crates/download-engine/README.md). نتائج الدفعة السابقة: 36/36 اختبار Rust (10 core، 9 resume، 3 engine، 14 store)، و21/21 مختبر HTTP، و13/13 تكامل executable. نجح البناء وfmt وClippy لجميع targets مع -D warnings. أُعيدت تجارب التكامل على executable المبني بعد إصلاح الإلغاء. المجموع 70 اختبارًا ناجحًا، دون ادعاء أنها تغطي تأهيل الإصدار الكامل.

تغطي تجارب المحرك: تنزيلًا ببصمة متوقعة، تحويلًا داخل الأصل، انقطاعًا ثم استكمالًا، تغير ETag بنفس الحجم، نطاقًا خاطئًا، تجاهل Range، رفض التصادم مع ملف المستخدم، قتل العملية بعد checkpoint ثم إعادة تشغيلها، بصمة خاطئة، تنزيلًا كاملًا بلا دعم Range، رفض تجاوز حد الحجم قبل إنشاء المهمة، ورفض تغيير الاسم أثناء الاستعادة وبعد الاكتمال.

اختبارات Rust تغطي أيضًا رفض نشر مهمة جاهزة عند اختلاف الرابط أو الاسم أو فقد قناة مالك المهمة، وتلف/قصر/زيادة الملف الجزئي، وعدم تقصير ملف مكتمل عدله المستخدم، والتوقف بين نية النشر وربط الملف وتسجيل النجاح.

اختبارات Node المباشرة تعمل محليًا. منع sandbox إنشاء عمليات المحرك أولًا بـspawn EPERM؛ أُعيد نفس اختبار التكامل بصلاحية موسعة وافقت عليها الأداة ونجح دون تخفيف الشروط. قتل العملية ليس فصل طاقة؛ محاكاة مراحل نية النشر لا تعادل حملة أعطال قرص شاملة.

### إصلاحات المراجعات

- فصل Store::open عن النشر حتى يطابق المحرك الرابط والاسم والبصمة وحد الحجم أولًا.
- منع تقصير الملفات المنشورة المعدلة، وفحص الحجم الدقيق والبصمة قبل النشر.
- رفض الملفات الخاصة والروابط المعروفة؛ لا ادعاء حماية كاملة من سباق برنامج آخر بنفس الحساب.
- فحص الإلغاء بين قطع الكتابة وبعد فتح التخزين وقبل النشر، واعتبار فقد قناة المالك إلغاءً.
- توثيق وجوب انتظار future بعد طلب الإلغاء؛ إسقاطه لا يوقف عامل القرص. النشر النهائي غير قابل للمقاطعة بعد دخوله.
- مراجعة نسخ التبعيات وتراخيصها وأربعة إشعارات محددة، وليست cargo audit شاملًا. [مراجعة الأمن](network-storage-security-review.md).

### قرارات وحدود صريحة

SQLite يستخدم DELETE journal مع synchronous=FULL لمالك واحد؛ هذا يختلف عن WAL المقترح للمعمارية الأوسع. نشر hard link حصري داخل مجلد المهمة، وتبقى وصلة part للاستعادة. مزامنة الدليل على Windows لم تنفذ؛ متانة فصل الطاقة بوابة مفتوحة.

مخطط SQLite v2 يحفظ بصمات الرابط الأصلي والنهائي بدل نصهما. تُرفض v1 القديمة دون تعديل أو ترحيل، ولا تنظف بياناتها القديمة. البصمة ليست تشفيرًا وقد تكشف التطابق أو تسمح بالتخمين؛ ETag والبيانات الأخرى غير مشفرة. حماية بيانات الاعتماد والبيانات الوصفية شرط قبل ربط المتصفح أو الاستخدام الإنتاجي. المدخل مستخدم محلي موثوق؛ سياسة DNS/IP بحسب مصدر الطلب لم تنفذ.

الناقل يتطلب Content-Length وهوية غير مضغوطة، ويقيد التحويلات بالأصل نفسه. لا يستكمل بلا ETag قوي. كامل الحجم بلا علامة نهاية سليمة لا ينشر تلقائيًا. نموذج حالات المجال محلي للاستدعاء، وليس بعد منسق مهام متعددًا أو سجل أحداث دائمًا.

أضيف اختبار HTTPS محلي بشهادة ذاتية مؤقتة؛ يثبت رفض شهادة غير موثوقة قبل HTTP أو إنشاء المهمة. لا يثبت بعد صلاحية مسارات HTTPS موثوقة أو شهادات منتهية أو اختلاف hostname؛ لا اختبار HTTPS خارجي. لا نتائج macOS/Linux أو حمل طويل أو قياس سرعة تنافسية. SHA-256 مستقل عن أصالة المصدر ما لم تتوفر بصمة موثوقة.

### الخطوة التالية حسب المخاطر

1. توسيع مصفوفة TLS واختبار امتلاء القرص وفشل المزامنة، ومخزن أسرار للبيانات الوصفية قبل توسيع المداخل.
2. تثبيت CI وبيئات الأنظمة الثلاثة؛ تجارب سطح المكتب والإتاحة ودورة حياة المحرك (DL-006).
3. منسق مهام دائم ومسارات إيقاف/استئناف/إعادة بدء واضحة، ثم النقل المتوازي وحدود المضيف وفق قياسات.
4. ربط تجربة سطح المكتب؛ استكمال بحث العملاء وتصميم الرحلات ثم الموقع التجاري والتفعيل.

DL-007 وDL-008 منفذان جزئيًا؛ معايير قبولهما الكاملة لم تغلق. الواجهة وإضافات المتصفح والوسائط والدفع والتراخيص والتحديث والتوقيع والتأهيل التجاري لم تنفذ. لا حماية كراك منفذة أو موعد إطلاق أو نسبة إنجاز إجمالية معتمدة.

### القرارات التجارية الثابتة

الدفع عبر موقع مستقل؛ التطبيق للتفعيل وحالة الترخيص وفتح الموقع. مقاومة العبث متعددة الطبقات دون وعد منع الكراك كليًا أو الإضرار بملفات المستخدم. جميع القرارات المهمة موثقة في Markdown. لا شراء أو تواصل خارجي أو نشر منتج حدث في هذه الدفعة.

### دفعة الخصوصية والإلغاء وTLS

استُبدل حفظ نص الرابط ببصمة مع إصدار مخطط صريح واختبارات عدم حفظ علامة الرابط ورفض v1 دون تعديلها. مراجعة Security المستقلة في [مراجعة الخصوصية](privacy-review.md). أضيف اختبارا إلغاء يحافظ فيهما الخادم على الاستجابة مفتوحة: طلب إلغاء ثم استكمال دقيق، وفقد قناة المالك دون نشر. اختبار TLS ينشئ شهادة ومفتاحًا مؤقتين في الذاكرة دون حفظهما أو تعديل مخزن الثقة؛ PowerShell 7 متطلب للمختبر. التحقق النهائي: 40/40 اختبار Rust (منها اختبارا شبكة للإلغاء و16 للتخزين)، و14/14 اختبار executable، و1/1 TLS على النسخة المبنية النهائية؛ fmt وClippy بلا تحذيرات. اختبارات الخادم لم يتغير كودها، ودليلها السابق 21/21؛ مجموع المجموعة 76 اختبارًا. فشل اختبار الإلغاء أولًا لأن socket المختبر ورث nonblocking على Windows؛ أصلح المختبر بوضع blocking صريح ثم نجح الاختباران والفحص الكامل.

### أخطاء التخزين بعد الحفظ الجزئي

التغيير المنفذ يشدد قاعدة إغلاق الكائن المتأثر عند فشل كتابة أو مزامنة أو إيصال حالة: إعادة فتح المهمة والتحقق من السجل والبايتات شرط لأي استكمال. أضيفت فئات أخطاء منقحة لتمييز تعارض الوجهة وتلف البيانات والبصمة وقفل المهمة وأخطاء I/O دون كشف مسارات أو روابط. مراجعة مستقلة وأدلة الاختبارات في [مراجعة أعطال التخزين](disk-failure-review.md). حقن الأخطاء ليس اختبار امتلاء قرص فعلي أو فصل طاقة.

وثّق نقاش العميل في [التثبيت والتجربة وإدارة الأجهزة](customer-installation-and-activation.md). مدد التجربة والاتصال وعدد الأجهزة ونطاق المجاني الدائم ما زالت مقترحات؛ لا رخصة أو موقع أو مثبت منفذ حتى الآن.


التحقق النهائي لهذه الدفعة على Windows: 49/49 Rust (25 تخزينًا، 10 مجال، 9 سياسة استكمال، 3 محرك، 2 إلغاء شبكي)، و15/15 تجربة executable. البناء وfmt وClippy لجميع targets بلا تحذيرات. لم يتغير مختبر الخادم أو مسار TLS؛ آخر دليل لهما 21/21 و1/1 من الدفعات السابقة. المجموع التراكمي 86 اختبارًا؛ ليس تأهيل منصة أو فصل طاقة. أُعيدت التجارب الفعلية بعد تغييرات التصنيف ومنع إعادة استخدام التخزين المتعثر.

### إدارة عدة مهام داخل العملية

أضيف مدير مهام في download-engine بطابور FIFO وحد عالمي للتنزيلات المتزامنة وأوامر إيقاف مؤقت واستئناف وإغلاق ينتظر عوامل النقل. snapshot يحتوي هوية وحالة وبايتات محفوظة دون روابط أو مسارات. الطابور في الذاكرة فقط، بينما checkpoints لكل ملف تبقى في transfer-store. لا تغيير في CLI أحادي الملف ولا واجهة رسومية حتى الآن.

دليل التصميم والحدود في [مدير المهام](task-manager.md)، والمراجعة المستقلة في [مراجعة المدير](task-manager-review.md). اختبارات الشبكة تغطي انتقال الخانة بعد الإيقاف، استكمال ملفين دون خلط، حد خانتين مع مهمة ثالثة منتظرة، إيقاف مهمة بالطابور قبل أول طلب، إغلاق المدير وفقد المالك وتحرير قفل التخزين. حفظ الطابور والجدولة الزمنية وحدود المضيف وسرعة النقل ما زالت لاحقة.

نتيجة دفعة مدير المهام على Windows: 58/58 Rust (10 مجال، 9 سياسة، 25 تخزين، 7 وحدات محرك ومدير، 2 إلغاء، 5 شبكة للمدير)، و15/15 تجربة executable على البناء النهائي. fmt وClippy لجميع targets نجحا بلا تحذيرات. الدليل السابق الذي لم يتغير مساره: 21 اختبار مختبر و1 TLS؛ المجموع التراكمي 95 اختبارًا. مراجعة مستقلة أغلقت إقرار pause عند فشل الحفظ والتباس أسماء Windows. لا دليل تشغيل للأنظمة الأخرى أو لطابور دائم بعد.

### تنظيم الطابور بحسب الأصل والأولوية

أضيف حد لكل أصل HTTP (scheme/host/effective port) مع الأولويات Low/Normal/High، مع حفظ FIFO عند التساوي، وتشغيل أصل آخر إذا امتلأ حد الأصل الأعلى أولوية. لا تقطع الأولوية تنزيلًا جاريًا. الحصة لا تتحرر حتى انتهاء العامل، بما فيه مدة حفظ الإيقاف. السياسة تخص كل Manager محلي، وليست حد معدل طلبات أو quota خادمية؛ [التفاصيل](scheduling-policy.md) و[المراجعة](scheduler-review.md).

اختبارات الشبكة الجديدة تستخدم خادمين محليين بمنافذ مختلفة للتحقق من حد الأصل وعدم تعطيل أصل آخر، وترتيب الأولويات وعدم المقاطعة وإعادة ترتيب المنتظر مع FIFO. لا دليل أداء واسع أو إنصاف لانتظار منخفض الأولوية تحت وصول مستمر بعد.

التحقق النهائي للجدولة: 64/64 اختبار Rust على Windows (10 مجال، 9 سياسة، 25 تخزين، 10 وحدات محرك ومدير، 2 إلغاء، 8 شبكة للمدير). fmt وClippy لجميع targets بلا تحذيرات. لم يتغير ناقل الملف أو fixtures في هذه الدفعة، فلم تُعد الاختبارات الخارجية غير المتأثرة؛ آخر دليلها 15 executable و21 مختبر و1 TLS. المجموع التراكمي 101 اختبارًا مع الفصل بين تشغيل هذه الدفعة والأدلة السابقة. المراجعة المستقلة بلا ملاحظات مانعة ضمن النطاق الداخلي.

### تحديد سرعة الملف

أضيف bytes_per_second اختياري لكل تنزيل، مع CLI --bytes-per-second. الانتظار قابل للإلغاء وحفظ التقدم، ويُحاسب الاستكمال على البايتات الجديدة فقط. هذه وتيرة استهلاك جسم الملف وليست عداد سرعة الشبكة الفعلية أو حدًا عامًا لمجموع المهام. [سياسة السرعة](bandwidth-policy.md) و[مراجعتها](bandwidth-review.md).

مراجعة الأمان والهندسة كشفت أن read_timeout في عميل HTTP قد يحتسب وقت تحديد السرعة؛ استُبدلت بمهلة 30 ثانية محيطة بانتظار طلب HTTP أو الجزء فقط، مع إبقاء مهلة الاتصال 15 ثانية. اختبار بطيء يتجاوز 30 ثانية مخصص لمنع عودة هذا الخلل. لا تغيير حي للحد داخل مهمة جارية، ولا توزيع سرعة عام بعد.

نتيجة دفعة تحديد السرعة على Windows: 69/69 Rust (12 وحدات محرك ومدير وسرعة، 3 شبكة للسرعة، وباقي المجموع السابق)، و16/16 executable، و1/1 TLS على البناء النهائي. اختبار بايت/ثانية تجاوز 33 ثانية وأكمل دون خطأ مهلة كاذب؛ اختبار إلغاء أثناء انتظار الحد استكمل لاحقًا بالبايتات نفسها. fmt وClippy لجميع targets بلا تحذيرات. آخر دليل مختبر الخادم غير المعدل 21/21؛ المجموع التراكمي 107. لم يُختبر بعد تعطل قراءة شبكة لمدة 30 ثانية في اختبار مستقل، ولا دقة معدلات عالية أو حد سرعة عام.


### دفعة القدرات الأربع

أضيف حفظ مشفر للطابور وخياراته على Windows، ونقل متوازٍ حتى ثمانية أجزاء للملف، وإعادة محاولة محدودة، وحد سرعة مشترك مع تعديل حي. هذه واجهات محرك داخلية؛ لا واجهة منتج أو مثبت بعد. دليل الاستخدام والقيود: [الطابور والمحاولات](durable-queue-and-retries.md)، [النقل المتوازي](parallel-downloads.md)، [السرعة](bandwidth-policy.md)، [المراجعة المستقلة](four-features-review.md). الأقسام السابقة سجل تاريخي؛ هذه الدفعة تحدث وصف الذاكرة فقط والاتصال الواحد والحد الثابت.

الطابور يستعيد المهام غير المكتملة متوقفة، ويحتاج resume أو resume_all. اللقطة مشفرة بـDPAPI لحساب Windows قبل SQLite؛ لا دعم حفظ مشفر على macOS/Linux بعد. التقدم الظاهر بعد الاستعادة آخر قيمة محفوظة، ويعيد الناقل التحقق من مخزن النقل عند الاستئناف. لم نثبت بعد قتل عملية المدير أثناء حفظ الطابور أو متانة انقطاع الطاقة.

المحاولات تشمل Network و408/500/502/503/504، بعدد أقصى مضبوط حتى خمس محاولات. 429 وأخطاء Retry-After لا يعاد جدولتها تلقائيًا. اتصالات الأجزاء تشترك في حدود السرعة؛ حصة الأصل ما زالت تحصي المهام وليس الاتصالات. حد السرعة لكل Manager ويقيس استهلاك الجسم، مع دلالة القطعة الجارية الموضحة في السياسة. نقل معروف الطول وهوية قوية، وذاكرة نطاقات محدودة، وبادئة متصلة محفوظة؛ ليست قياسات سرعة تنافسية أو تأهيل إصدار enterprise.

التحقق النهائي على Windows x64: نجح 92 اختبار Rust مختلفًا (91 في تشغيل workspace ثم اختبار تكامل جديد ضمن تشغيل اختبارات parallel التسعة)، و17 تجربة executable، واختبار TLS واحد. المجموع المشغل لهذه الدفعة 110؛ آخر دليل للخادم غير المعدل 21 اختبارًا ناجحًا، فيصبح الدليل التراكمي 131. نجح البناء وClippy لجميع targets مع منع التحذيرات؛ فُحص التنسيق. الاختبار الجامع أثبت 4 اتصالات ثم 503 وإعادة محاولة ناجحة وتطابق الملف، وبعد إعادة فتح المدير أثبت بقاء الحالة وحد الملف والسقف العام بقياس تنزيل جديد. أصلح تعارض أسماء مجلدات الاختبارات باستخدام عداد ذري، ثم نجحت الإعادة. لا يحول هذا الدليل المحلي إلى اعتماد إنتاجي للأنظمة الثلاثة.

### استكمال توافق المحرك وإدارة الملفات

أضيفت RequestPolicy للاعتماد وCookie الخام من المتصل المحلي الموثوق، مع تحقق الحدود ورفض حقن الرؤوس وتنقيح Debug، وحذف الاعتماد عند التحويل إلى أصل آخر مصرح به ومنع خفض HTTPS. تحفظ الخيارات داخل لقطة الطابور المشفرة v2، مع قراءة v1 القديمة بسياسة طلب فارغة. ليست Cookie jar بدلالات المتصفح.

يدعم الناقل ملفات مجهولة الحجم ذات تأطير chunked سليم، بسقف على البايتات الفعلية، ولا ينشر عند فقد خاتمة الاستجابة أو الإلغاء. تحفظها قاعدة نقل v3؛ تبقى v2 المعروفة مدعومة. المجهول المنقطع يحتفظ ببياناته ويرفض الاستكمال دون دليل؛ يعاد البدء بمهمة جديدة. تجديد query لرابط مؤقت متاح لمهمة متوقفة مع SHA-256 موثوق محفوظ، وETag قوي وطول معروف؛ يرفض تغيير الأصل أو المسار.

أضيف فحص استرشادي للمساحة قبل النقل والتصدير، وتصدير ملف مكتمل إلى وجهة أخرى مع مقارنة بصمة النسخة ومنع الاستبدال وسياسات Reject/Skip/Rename. تنظف العملية مؤقتها عند الخروج العادي؛ لا حذف للملفات الجزئية. إزالة مهمة من القائمة تحفظ العداد وتبقي الملفات. أضيف Inbox داخلي محدود لفصل الاقتراح عن الموافقة المحلية؛ ليس بعد إضافة متصفح أو قناة اتصال مصادقًا عليها.

التفاصيل: [الطلبات](request-compatibility.md)، [المجهول](unknown-length-transfers.md)، [الروابط المؤقتة](signed-url-refresh.md)، [الوجهات](file-destinations.md)، [الاستقبال](application-intake.md)، [المراجعة](remaining-engine-review.md)، [التأهيل](engine-qualification.md). أضيف workflow للأنظمة الثلاثة؛ وجوده لا يعني نجاح تشغيلها. يُسجل أدناه دليل التشغيل الفعلي لهذه الدفعة.

لا تزال بوابات الإطلاق مفتوحة: إضافة المتصفح وقناة native messaging المصادق عليها وسياسات DNS/IP، واجهة سطح المكتب، مخزن أسرار macOS/Linux، تنظيف المؤقتات بعد انهيار العملية، قياسات الاستجابة للملفات الكبيرة، وتشغيل طويل وأعطال مادية وتأهيل أنظمة فعلي. تتطلب هذه البنود تنفيذًا وأدلة قبول مستقلة.

نتيجة هذه الدفعة على Windows x64: نجح 119 اختبار Rust في workspace ثم اختبار النقل الاختياري 64MiB (28.19 ثانية)، ليصبح مجموع Rust المشغل 120. نجحت 18 تجربة executable و21 تجربة مختبر و1 TLS؛ مجموع الاختبارات المختلفة المشغلة 160. نجح build وfmt وClippy لجميع targets مع -D warnings. فحص المساحة كشف أثناء المراجعة خطأ الاستكمال بمسار نسبي؛ أصلح بتحويل المسار إلى مطلق، ونجح اختبار executable مخصص على البناء النهائي. نتيجة 64MiB دليل نقل محدود لا تأهيل ملفات ضخمة أو تشغيل لأيام. لم تشغّل هذه البيئة macOS/Linux ولا أعطالًا مادية.

### إقرار قبول الطلبات ومنع التكرار

تضيف هذه الدفعة قبولًا دائمًا بمعرف طلب: المهمة وإقرارها يحفظان في لقطة مشفرة واحدة قبل الرد أو بدء العامل. إعادة الطلب بالمعرف والخيارات الأصليين تعيد المهمة نفسها بعد إعادة التشغيل؛ اختلاف الخيارات يرفض، وإزالة المهمة تبقي علامة تمنع إعادة إنشائها بطلب قديم. لا إقرار دائم من Manager المؤقت. يربط Inbox هذه الدلالة بهوية مصدر ثابتة يحددها المتحكم الموثوق، مع بقاء الموافقة المحلية شرطًا قبل الإنشاء.

هذا تنفيذ لجزء قبول الطلبات في عقد الربط؛ لا إضافة متصفح أو listener أو مصادقة مصدر خارجي بعد. قائمة الاقتراحات نفسها مؤقتة؛ الإقرار يحفظ للطلبات التي وافق عليها المستخدم فقط. التفاصيل والحدود في [الإقرار الدائم](durable-admission.md)، [استقبال الطلبات](application-intake.md)، [المراجعة](durable-admission-review.md). تسجل نتائج الاختبارات بعد إتمام التحقق أدناه.

### تحقق أساس المعمارية الجديدة

اكتمل CI للكود `4d656217335acd7428555047df89ec3824ba8aab` بنجاح على Windows 2022 وmacOS 14 وUbuntu 24.04: [تشغيل الأساس](https://github.com/FMalki1406/FHD/actions/runs/35640570877). هذا اعتماد اختبارات هذه الدفعة، وليس إكمال مراحل الوثيقة أو قياسات الأداء. تفاصيل التقدم الحالي في [سجل التطبيق](enterprise-implementation-status.md).

### التخزين الموضعـي وSQLite ومسار الكاتب

أضيفت محولات fhd-storage وfhd-persistence ومسار fhd-runtime. تخزين الملفات يقبل الكتابة خارج الترتيب ويتحقق من التغطية والبصمات ويحمي الجيل المنشور. مستودع SQLite ينفذ قبول الأمر والمهمة والإيصال في معاملة واحدة مع WAL/FULL وحدود سعة وتصريح يسبق جدولة العمل المحجوب. BufferPool يعيد استخدام كتل ضمن ميزانية مشتركة؛ Writer يجمع الكتابات المتجاورة ويحافظ على حواجز sync ويصرف العمل المقبول عند الإلغاء. أخطاء التخزين تعرض رموزًا ثابتة تميز امتلاء القرص والصلاحية والمهلة وغيرها دون مسار أو رسالة SQLite خام.

نجح الفحص الشامل على Windows بـ191 نتيجة Rust ناجحة، منها مدخل مساعد لاختبار العملية الفرعية. بعد إضافة اختبار رموز أخطاء التخزين نجحت إعادة الوحدات المتأثرة بـ34 نتيجة؛ الدليل التراكمي دون عد الإعادات 192 مدخلًا، منها 191 اختبارًا سلوكيًا ومدخل العملية المساعد. بقي اختبار64MiB الاختياري مستثنى. نجحت8 اختبارات بوابة المعمارية وفحص metadata للحزم14، وClippy لكل targets دون تحذيرات والتنسيق.

اختبار الانهيار يقتل عملية بعد commit مع بقاء اتصال SQLite مفتوحًا، ثم يثبت استعادة المهمة والإيصال نفسه ورفض تغيير مواصفات المفتاح. لا يثبت فصل الطاقة أو قتلًا عشوائيًا أثناء كل خطوة. عولجت ملاحظات المراجعة المستقلة عن تصاريح SQLite ومزامنة دليل الأب وختم الجيل وحماية المستعاد وتجميع الكتابات.

حدود الدفعة: لا مستودع extents أو PublishIntent دائم بعد، ولا ربط للكاتب الجديد بـHTTP أو Scheduler. النشر hard link فقط بلا fallback عبر الأقراص، ومخزن الأسرار والسياسات المؤسسية وIPC مفتوحة. لم يُستبدل المحرك القديم ولم تُقَس أهداف الأداء. [سجل التطبيق التفصيلي](enterprise-implementation-status.md) يفصل هذه الحدود؛ نتائج CI لهذه الدفعة تضاف بعد تشغيلها.

تشغيل [35643157056](https://github.com/FMalki1406/FHD/actions/runs/35643157056) للكود `a679132e2b9d051b3335d9bccb9a36fe5d1cc922` نجح على Windows وmacOS وفشل على Linux في قيد زمن اختبار تحديد السرعة القديم: كان يحسب تجهيز الاتصال والمخزن ومزامنة القرص ضمن حد3 ثوانٍ للإلغاء. نتيجة الإلغاء نفسها صحيحة، لكن القيد الشامل فشل. فصل الإصلاح بين اختبار التكامل الذي يحتفظ بإثبات البادئة والاستكمال، واختبار وحدة حتمي يبدأ بانتظار Pending ثم يلغي ويشترط Ready(Cancelled) في poll التالي للحد الفردي والعام مع تحرير الأقفال. راجع Engineering هذا الفصل؛ لم يتغير سلوك الإنتاج ولم يُرفع حد زمني لإخفاء الفشل. نتائج إعادة CI تسجل بعد اكتمالها.

**النتيجة النهائية:** نجح [تشغيل35644474152](https://github.com/FMalki1406/FHD/actions/runs/35644474152) للكود `51de1bb60282626924799e0a51b659f2bdaf9edd` على Windows2022 وUbuntu24.04 وmacOS14. شمل التنسيق وحدود المعمارية وClippy واختبارات Rust وبناء أداة النقل والمختبر والتنزيل الفعلي، إضافة إلى TLS على Windows. سبق الرفع نجاح خمسة اختبارات إلغاء محلية ذات صلة وفحص Clippy بعد تصحيح الاختبار. أُغلق فشل Linux؛ لا فحص CI معلق لهذه النسخة. نجاحها يثبت هذه الدفعة ضمن الحدود الموثقة ولا يكمل بقية مراحل المعمارية.

### المحرك الجديد: من وحدات مستقلة إلى خدمة تعمل

بعد دفعة التخزين وSQLite، وُصل المحرك الجديد طرفًا إلى طرف ثم صار خدمة مقيمة. اثنتان وعشرون دفعة بين `51de1bb` و`0a3b867`، كلها خضراء في CI على Windows 2022 وUbuntu 24.04 وmacOS 14. التفصيل في [سجل التطبيق](enterprise-implementation-status.md)؛ هنا ما تغيّر فعلًا وما لم يتغيّر.

### ما صار يعمل

- **تنزيل حقيقي ينتهي بملف منشور.** منسق المهمة يفحص ويقسّم ويشغّل اتصالات متوازية، ويثبّت التقدم بنقاط تفتيش ببصمات لكل نطاق، ويتحقق من الملف كاملًا، ثم ينشره تحت نية مسجلة تُصالَح بعد التعطل. تصحيح توثيقي 2026-09-23: الآلية في المصدر hard link بلا استبدال ثم تحرير part، وليست إعادة تسمية كما كُتب سابقًا. الاستئناف مربوط بمعرّف تمثيل قوي: لا تُلحق بايتات لتمثيل لا يمكن إثبات أنه هو نفسه.
- **عدة مهام تحت سقوف.** مجدول يقرر من يعمل بثلاثة سقوف (لمهمة، وللمحرك كله، وعدد المهام معًا)، وحاكم لكل أصل يملك سقف اتصالاته ومهلة `Retry-After` التي يطلبها الخادم، منفصلة عن تراجعنا الأسي ومحدودة بسقف.
- **ذاكرة بين التشغيلات.** مخزن مراجع يحفظ ما تشير إليه كل مهمة، فيكمل `--continue` ما بدأه تشغيل سابق بلا روابط جديدة. الرابط المعلَّم حسّاسًا لا يُكتب على القرص إطلاقًا (اعتماد المستخدم، 2026-09-23).
- **سطح تحكم محلي.** عقد أُطر بإصدار وحدود، ومقبس Unix/أنبوب Windows لكل مستخدم، و`--serve` يستقبل العمل أثناء تشغيله ويجيب عن حالته ويتوقف عند الطلب.

### دليل التحقق

كل دفعة مرّت محليًا على Windows بـfmt وبوابة المعمارية وclippy بمنع التحذيرات والحزمة كاملة، ثم CI على الأنظمة الثلاثة. أُعيد إنتاج كل إخفاق Linux داخل حاوية محلية قبل إصلاحه. اختبارات طرف إلى طرف تستعمل محولات حقيقية: خادم HTTP محلي وSQLite على القرص وملفات part فعلية، بلا مزيفات في ذلك المسار. وجرى **تشغيل يدوي للثنائي**: ملفان (3 MB و1.5 MB) نُزّلا معًا ونُشرا ببصمتين مطابقتين ولم يبقَ في مجلد الأجزاء سوى قفل الملكية.

ثلاثة عيوب حقيقية كشفها التشغيل الفعلي لا الاختبارات، وهي أهم ما في هذه الدفعات: قفل ملكية بنطاق خاطئ كان يمنع مهمتين متوازيتين؛ ومعرّفات مراجع من بصمة كانت تفشل في نصف الحالات عند حفظها؛ ومهام عملاء تعيش بعد إيقاف خادم الـIPC فتمسك قاعدة البيانات. الاختبار الذي كان يُفترض أن يغطي الأول كان يمنح المحرك اتصالات بقدر مهمة واحدة، فلم تتوازَ مهمتاه أصلًا.

### ما لم يتغيّر ولا يُدّعى

- **المحرك القديم ما زال مسار `fhd-transfer`** التنفيذي؛ لم يُستبدل ولم تُحذف ازدواجية الحالة فيه.
- **لا قياسات أداء.** أهداف §1 (سرعة، عدد مهام، استهلاك) لم تُقَس ولا يوجد benchmark. «يعمل» ليست «يحقق الهدف».
- **Windows أضعف مما تصفه المعمارية** عند حد الثقة: لا DACL صريحة للمالك على الأنبوب ولا تحقق من مالكه في العميل، لأن كليهما يحتاج استدعاءات win32 غير آمنة والـworkspace يمنع `unsafe`. قرار مطلوب من المستخدم.
- **لا واجهة ولا امتداد متصفح ولا ترخيص إنتاجي ولا توقيع ولا تحديث**، ولا خدمة نظام (Service/launchd/systemd)، ولا عميل سطر أوامر للخدمة بعد.
- **لا مخزن أسرار نظام** (DPAPI/Keychain/Secret Service)، ولا سياسة مؤسسية (GPO/MDM)، ولا fuzzing ولا SBOM ولا اختبار فصل طاقة.
- سجلات CI غير مقروءة من هذه البيئة بلا رمز وصول؛ إخفاق Windows الأخير لم يُقرأ سجله ولم يتكرر محليًا، وعولج المسار المرجَّح دون إثبات أنه السبب.

### قيد في التحقق، وما فُعل حياله (2026-09-23)

أخفق اختبار Windows في CI على **دفعة توثيق فقط** (`52df545`) لم تمس سطرًا من الكود. أي أن هناك اختبارًا هشًّا على عدّاء Windows، وليس انحدارًا في ميزة. محليًا: عشر تشغيلات كاملة متتالية نظيفة، وتشغيلة مثبّتة على نواتين (كعدّاء CI) نظيفة — فالهشاشة تخص بيئة العدّاء لا الكود كما نراه هنا.

**المشكلة الأعمق أن السجل غير مقروء:** واجهة سجلات Actions ترفض بلا رمز وصول (403)، وواجهة التعليقات ترد 404، وصفحة المهمة لا تتضمن السجل. جُرِّبت أربع طرق. لذلك عولج إخفاق Windows سابقًا **بالترجيح** (`StateBusy`) ولم يُثبت أنه كان السبب، وقد سُجّل ذلك.

**ما فُعل بدل الترجيح:** قُسّمت خطوة الاختبار في CI إلى سبع خطوات بحسب المجال. أسماء الخطوات ونتائجها **مقروءة بلا رمز وصول** بعكس السجل، فصار إخفاق على عدّاء لا نستطيع محاكاته يدل على موضعه بنفسه. هذا لا يعطي رسالة الاختبار، لكنه يحوّل «فشل شيء ما على Windows» إلى «فشل في هذا المجال».

**ما زال مطلوبًا من المستخدم:** رمز وصول للقراءة، أو لصق مقطع الإخفاق. بدون ذلك تبقى رسالة الاختبار الفعلية خارج متناولنا.

## التعافي على مستوى الوظيفة (2026-09-25)

القسم ٩ من `docs/publication-contract.md` جعل حالة النشر **مقروءة** من القرص. هذه الدفعة تصل تلك القراءة **بقرار الوظيفة**، والتفصيل في القسم ١٠ من الملف نفسه.

### ما صار يعمل

| الحالة على القرص | السبب المسجَّل | ما يفعله «استئناف» |
| --- | --- | --- |
| صيغة لا يقرؤها هذا البناء | `Unreadable` | جيل جديد وكائن مستقل؛ الجزء القديم يبقى بلا كتابة |
| فساد سجل أو هوية جزء | `Integrity` | جيل جديد، بالشروط نفسها |
| خُتم وبُدئ الربط، والنتيجة مجهولة | `Unconfirmed` | **لا شيء تلقائيًا**: توقف بالسبب نفسه، بلا إعادة تنزيل وبلا فكّ ختم |

وأُضيف `Unconfirmed` إلى مخزن المهام، ووُسّع فحص المخطط إلى ٩ بالترحيل `005_stop_reasons.sql`.

**وهنا سجّلت عيبًا لم يكن موجودًا، مرتين.** قلت أولًا إن `reason BETWEEN 0 AND 6` كان يمنع تسجيل `Destination` (٧) فترجع الوظيفة `PERSISTENCE-UNAVAILABLE`؛ ثم ضيّقت ذلك — بعد مراجعة هندسية — إلى القواعد الأقدم من `5799bab`. وطعنت المراجعة الأمنية في الاثنين، والفحص يحكم لها:

- الالتزام `5799bab` أضاف `Destination` **ووسّع ٠٠٣ إلى `BETWEEN 0 AND 7` في الالتزام نفسه**.
- والقاعدة التي تحمل ٠٠٣ القديم لا تعمل بالفحص الضيّق: `validate_schema` يقارن **بصمة كل ترحيل مُطبَّق**، فترفض القاعدة عند الفتح بـ`Corrupt` بدل أن تُفتح بالفحص القديم.

فلا قاعدة رفضت يومًا سببًا ينتجه المحرك، والعيب الحقيقي هو الرمزان الجديدان فقط. **وهذا حلٌّ صريح لتعارض بين المراجعتين**، كما يوجبه `AGENTS.md`.

**ثم أخطأت مرة ثالثة في الفقرة نفسها.** كتبت أن «الذي يبقى من الملاحظة» هو أن `5799bab` عدّل ترحيلًا مطبَّقًا في مكانه. و`git show --name-status 5799bab` يقول `A`: **أنشأ** ٠٠٣ ملفًا جديدًا يعيد بناء الجدول ويوسّع الفحص — أي عين الممارسة التي كنت أوصي بها. والفحص الضيّق `0..6` كان في ٠٠٢، وقد تجاوزه ٠٠٣.

فلم يبقَ من الاعتراض شيء إلا الشكل القائم فعلًا: **توسيع أي `CHECK` بملف ترحيل جديد**. والدرس الحقيقي أن ثلاث صياغات خاطئة لتعليق من خمسة أسطر تعني أن **ادعاءً عن التاريخ لا يساوي أكثر من الأمر الذي يتحقق منه**.

### دليل التحقق

ثلاثة اختبارات `end_to_end` مذكورة بأسمائها في القسم ١٠، مع **قياس طفرة على كل منها** — وأهمّها أن إدخال `Unconfirmed` في قائمة الاستبدال يجعل المحرك ينشر نسخة ثانية فعليًا، فيسقط الاختبار. وعلى هذا الجهاز: `fmt --check` و`clippy` على هدفَي Windows وLinux وبوابة المعمارية بلا ملاحظات، و٣٨١ اختبارًا في مساحة العمل بلا فشل.

### ما لا يُدّعى

- **الحالة المجهولة لم تُحسم**، إنما مُنع الضرر التلقائي. حسمها يحتاج إجراءً يقارن الوجهة الفعلية، وهو غير منفَّذ.
- **تنظيف جزء مرفوض غير منفَّذ**؛ يبقى على القرص.
- **Linux وmacOS بلا آلية نشر**، فالاختبارات الثلاثة تُقاس هناك على عقد «لا نشر والبايتات محفوظة».
- **لا اعتماد لم٣ أو ن٤**، وحظر الإصدار مستمر.

### المراجعتان المستقلتان، وما غيّرتاه

أُجريت مراجعة هندسية ومراجعة أمنية مستقلتان على `dc17a99`. لم تكن أيٌّ منهما تصديقًا: **وجدتا عيوبًا في الكود الذي كتبته، وأخطرها عيبٌ أدخلتُه أنا.**

| ما وُجد | من | الحال |
| --- | --- | --- |
| `Unreadable` و`Integrity` يفتحان باب **نشر نسخة ثانية** من ملف ربما سُلّم، وهو ما رُفع إصدار الصيغة لمنعه | أمنية | **مُصلَح**: حالة النشر تُقرأ أولًا، وعند غيابها يُستشار `publish_intents`. ولكلٍّ من النصفين اختبار (انظر أدناه) |
| قائمة الأسباب مكتوبة مرتين، والنسختان **اختلفتا فعلًا** | هندسية | **مُصلَح**: `blocks_resume()` و`needs_new_representation()` في المجال هما المصدر الوحيد |
| `ReplaceRepresentation` **لم يكن يرفض** `Unconfirmed` في المجال؛ الحماية كلها كانت في فرعٍ واحد بجذر التركيب | أمنية، وأكّده اختبارٌ كتبته للسياستين | **مُصلَح**: الانتقال يرفضه |
| اختبار «التعطل أثناء انتقال الجيل» **لا يبلغ النافذة**؛ محفّزه يتحقق بسبر الاستئناف | هندسية | **أُعيد ضبطه وأُعيد تسميته**، والنافذة الحقيقية مسجَّلة كغير منفَّذة |
| صف `Integrity` في العقد **مُدّعى بلا اختبار** | هندسية | **أُضيف اختبار** |
| ادعاء عيب المخطط (`Destination`) **غير صحيح** | أمنية | **صُحّح**، والتعارض بين المراجعتين محلول أعلاه |
| **بايت NUL خام** في جذر التركيب يجعل git يقارن الملف كثنائي، فلا يُراجَع أي تغيير فيه | المراجعتان معًا | **مُصلَح** (`\x00`، بايتات متطابقة فلا يتغيّر وسم المجلد)، **وبوابة المعمارية ترفضه الآن** |
| لا اختبار دوران لرموز الأسباب | أمنية | **أُضيف** |

وبنودٌ **لم تُنفَّذ** مسجَّلة في القسم ١٠ من عقد النشر: الإلغاء يحذف دليل النشر، ورسالة التوقف تنصح بالاستئناف، وأسماء الأسباب بلا تعداد معلن في `protocol`، وحقن خطأ داخل نافذة الانتقال، وتجزئة سجل الجزء.

**وهذه التغييرات نفسها غير مُراجَعة بعد**، لأنها جاءت بعد المراجعتين.

### الجولة الثانية: ما وجدته إعادة المراجعتين على `579e508`

أكّدت المراجعة الأمنية أن الإصلاح المركزي سليم — حاولت نقضه فلم تجد طريقًا يُستبدل به جزءٌ ربما سُلّم. ومع ذلك وجدت الجولة عيوبًا، منها ارتدادٌ أدخلتُه أنا:

| ما وُجد | الحال |
| --- | --- |
| **ارتداد**: كل خطأ تخزين عند الفتح كان يسقط على شاهد سجل الوظيفة، فخطأ مشاركة ملف عابر على Windows يحوّل وظيفة قابلة للاستئناف (`Storage`) إلى `Unconfirmed` الذي لا مخرج منه | **مُصلَح**: الشاهد الثاني يُستشار **فقط** حيث يكون السبب مما يُجاب عنه بإعادة التنزيل؛ و`Storage` لا يُستبدل أصلًا فلا يحتاجه |
| **نصف `Integrity` بلا اختبار**: أثبتته المراجعة بطفرة — قدّمت `Err(Integrity)` على فحص حالة النشر **فنجحت المجموعة كلها** بينما صار جزءٌ ربما سُلّم قابلًا للاستبدال | **مُصلَح باختبار** `corrupt_bytes_on_a_part_that_may_be_delivered_are_not_replaced`. وأول صياغة كتبتها له **نجحت تحت الطفرة نفسها** لأن الإيقاف المؤقت لا يترك امتدادات مثبتة، فأُعيدت بناءً على تشغيل مكتمل رُفض نشره |
| الخطأ المُبتلَع في فرع `unknown`: قرص يتعطّل لا يُميَّز عن نشر مجهول | **مُصلَح**: يُصدر `StorageFailed` قبل التوقف |
| السياستان مكتوبتان بـ`matches!`، فسببٌ جديد يصير «قابلًا للاستئناف، بلا استبدال» صامتًا | **مُصلَح**: `match` شامل، فالبناء يتوقف حتى يُصنَّف |
| لا شيء يؤكد أن `needs_new_representation ⊆ blocks_resume`، وترتيب الجذر يعتمد عليه | **مُصلَح**: تأكيد في اختبار المجال |
| بوابة NUL تمسح `crates/**/*.rs` فقط — فلا ترى `tools/` ولا `.sql` حيث تعيش قيود `CHECK`، ولا مصدر البوابة نفسها | **مُصلَح**: تمسح `crates` و`tools` و`.github` وامتدادات المنطق، **مع اختبار** كنت قد ادّعيته ولم يكن موجودًا |
| ادّعاء تاريخي ثالث خاطئ عن الترحيل ٠٠٣ | **مُصحَّح** أعلاه |

**ومفتوح ولم يُصلَح بعد:** `Unconfirmed` **لا مخرج منه في المنتج** — و`Cancel` يُهمَل بينما يُبلَّغ العميل `Done`. مسجَّل في القسم ١٠ من عقد النشر.
