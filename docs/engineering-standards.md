# معايير كتابة الكود والمراجعة

تحديث الحالة: 2026-09-23. المالك الوظيفي: Engineering بالتعاون مع Security وQA. هذه قواعد هندسية؛ Rust مستخدم في المحرك ووحدات الدومين والتطبيق والمحولات، وتعريف CI بعيد موجود مع نتائج تاريخية على الأنظمة الثلاثة. [سجل التطبيق](enterprise-implementation-status.md) يحدد حالة النسخة والحدود، و[سجل الأدلة](execution-status.md) يحدد ما شُغّل. Tauri وReact/TypeScript لا يعني ذكرهما هنا وجود واجهة منتج منفذة.

## فصل المسؤوليات

| الطبقة | تملك | لا تملك |
| --- | --- | --- |
| نطاق المحرك | حالات التنزيل، هوية التمثيل، تقسيم النطاقات، سياسة السلامة | واجهة React أو وصولًا عشوائيًا للشبكة والملفات |
| حالات الاستخدام | تنسيق العمليات والتحقق من الصلاحية والاستحقاق قبل قبول العملية التجارية | الاعتماد على boolean ترسله الواجهة لإثبات الدفع |
| محولات النظام | HTTP، SQLite، الملفات، مخزن الأسرار، IPC | إعادة تفسير قواعد الاكتمال أو الترخيص بطريقة مختلفة |
| الواجهة والإضافة | عرض حالة مرجعية، جمع مدخلات، إرسال أوامر محددة | مفاتيح توقيع خاصة أو أوامر shell عامة أو قرار ترخيص موثوق |
| خدمة الاستحقاق | حقيقة الحساب والشراء والأجهزة والخدمات التابعة لها | استقبال روابط التنزيل أو Cookies لأجل التحقق التجاري |

التدفق المخطط: واجهة ← نتيجة أمر؛ أمر → تحقق مدخلات → تحقق استحقاق في طبقة التطبيق → تنفيذ حالة استخدام → نتيجة موثقة. المحرك لا يخلط كتابة البايتات مع فحوص ترخيص متكررة لكل قطعة. نقاط منح الميزات تحدد في عقد واضح وتختبر باستدعائها دون الواجهة. لا توجد آلية محلية تجعل جهازًا يسيطر عليه المهاجم حد ثقة مطلقًا؛ القرار المحلي يرفع كلفة التجاوز ولا يضمن منع الكراك. فشل الاستحقاق لا يحذف الأجزاء أو يمنع الوصول لملفات العميل الموجودة.

لكل حد ثقة مخطط إدخال بإصدار، حد للحجم والعدد، أخطاء معلومة، وسياسة توافق. نوع TypeScript وحده ليس تحققًا من بيانات واردة أثناء التشغيل. صلاحيات Tauri تقيد لكل نافذة/مكون؛ لا تعوض تحقق الأمر داخل المحرك. [مرجع الصلاحيات الرسمي](https://v2.tauri.app/security/capabilities/).

## قواعد Rust

- وحدات منطق المنتج تبدأ بـ`#![forbid(unsafe_code)]`. أي احتياج خاص للنظام يعزل في وحدة أو crate صغيرة منفصلة ذات واجهة آمنة؛ لا يُخفض المنع في كامل المحرك لأجل استثناء واحد.
- كل `unsafe` يتطلب تعليق `SAFETY` يشرح ملكية الذاكرة وصلاحية المؤشرات والعمر والتزامن، ومراجعة Engineering وSecurity مع اختبار مناسب. لا يكفي أن الاختبار نجح لإثبات سلامة الذاكرة. يمنع `unsafe impl Send/Sync` بلا حجة موثقة.
- أخطاء الشبكة والقرص والتحقق والإلغاء نتائج متوقعة عبر `Result` وأنواع أخطاء واضحة. يمنع `unwrap` و`expect` و`panic!` في مسارات مدخلات المستخدم والشبكة والتخزين؛ الاستثناء لثابت داخلي مثبت يحتاج تفسيرًا ومراجعة. الاختبارات مسموح لها استخدام assertions.
- افصل رمز الخطأ القابل للمعالجة ورسالة المستخدم عن التفاصيل الداخلية المنقحة؛ لا تضيع سلسلة السبب ولا تسرب أسرارًا. لا تحويل خطأ كتابة أو مزامنة إلى نجاح صامت.
- الحسابات الخاصة بالأحجام والإزاحات checked، والنطاقات نصف مفتوحة داخليًا بعقد موحد. التحويل إلى HTTP أو أنواع منصة مختلفة يتحقق من الفائض والحدود.
- FFI محصور: تعريف ABI، أحجام، ownership، التحرير، thread affinity وعمر callbacks. لا عبور panic/exception للحد الأجنبي دون عقد ABI ومعالجة مصممة؛ لا افتراض أن مكتبة C آمنة للتزامن. [Rustonomicon: FFI](https://doc.rust-lang.org/nomicon/ffi.html).

## التزامن والحفظ

- كل مهمة خلفية لها مالك ودورة حياة وإلغاء ونتيجة مراقبة؛ لا مهام منسية تفشل بصمت. اذكر ما يحدث عند إغلاق الواجهة وإيقاف المحرك كلًا على حدة.
- طوابير وbuffers وحدود اتصال محدودة مع backpressure. لا تحميل ملف كبير كاملًا في الذاكرة، ولا تجميع دفعات المستخدم بلا حد.
- لا قفل blocking محجوز عبر `await`. حدد ترتيب الأقفال عند الحاجة لأكثر من قفل، وافصل أعمال القرص/المعالجة الثقيلة عن مسارات الاستجابة.
- الإلغاء يشمل انتظار الشبكة والقرص والطوابير. سقوط future ليس دليلًا أن أثر العملية الخارجية لم يحدث؛ كل إجراء غير قابل للعكس يحتاج reconciliation أو منع تكرار.
- ساعة monotonic للمهل داخل العملية؛ وقت التقويم له دور منفصل في الجدولة وصلاحية الاستحقاق. تبديل ساعة الجهاز حالة اختبار، وليس دليل احتيال كافيًا وحده.
- مالك واحد للحالة المرجعية؛ نتائج الأجزاء القديمة لا تدخل generation جديدًا. الإكمال يعتمد على التحقق والنشر الآمن وفق [المعمارية](architecture.md)، وليس نسبة تقدم الواجهة.

## TypeScript وReact

- `strict` مع `noUncheckedIndexedAccess` و`exactOptionalPropertyTypes` كإعداد عمل مستهدف؛ الاستثناء الضيق يوثق. الحزمة `strict` تشغل فحوصًا إضافية للأنواع وفق [مرجع TypeScript](https://www.typescriptlang.org/tsconfig/strict.html).
- لا `any` أو تجاهل عام للأخطاء لمعالجة حدود IPC؛ استخدم `unknown` ثم تحققًا فعليًا. أنواع ورسائل الواجهة والمحرك تتولد من مصدر عقد واحد أو تفحص اتساقها آليًا.
- حالة المحرك هي المرجع؛ التحديث المتفائل لأوامر الإلغاء/الإكمال لا يعرض نجاحًا قبل إقرار الحالة المطلوبة. فصل loading/error/cancelled/complete بأنواع واضحة.
- تنظيف الاشتراكات والمؤقتات والطلبات عند نهاية عمرها، ومنع استجابة قديمة من استبدال حالة أحدث. لا أحداث تقدم غير محدودة في state.
- لا HTML مشتق من اسم ملف/خادم دون معالجة مناسبة، ولا `eval`، ولا ربط URL مباشرة بفتح برنامج أو shell. الملفات والأسرار والتراخيص تمر بأوامر ضيقة.
- تختبر تدفقات لوحة المفاتيح وRTL والإتاحة مع حالات الفشل، وتبقى النصوص قابلة للترجمة ورموز الأخطاء مستقرة.

## التبعيات والبناء

أي تبعية جديدة لها غرض ومالك ورخصة ومنشأ وحد أدنى للصلاحيات وتقييم صيانة؛ راجع build scripts والتبعيات الانتقالية والشفرة الأصلية. لا خوارزمية تشفير خاصة بنا ولا أسرار إصدار في المصدر أو التطبيق. اعتماد مكتبة توقيع أو TLS يحتاج مراجعة Security.

ثبت نسخة toolchain وصورة CI وأداة إدارة الحزم؛ احفظ `Cargo.lock` للتطبيق وملف قفل JavaScript عند دخول تبعياته. يسجل Cargo.lock النسخ الدقيقة المحلولة وفق [Cargo Book](https://doc.rust-lang.org/cargo/guide/cargo-toml-vs-cargo-lock.html). نطاق النسخ في manifest ليس بديلًا عن القفل. تستخدم وظائف البناء أوضاع التثبيت المقفلة، وتفشل إذا غاب القفل أو احتاج تعديلًا. تثبيت النسخ لا يعني تجميدها للأبد؛ تحديثات دورية بمراجعة واختبارات، وعاجلة للثغرات المؤثرة.

مع كل حزمة إصدار: هوية المصدر، النسخ والأعلام، قائمة مكونات ورخص، بصمة الحزمة، تقرير الفحص والتوقيع. هدف البناء القابل لإعادة الإنتاج يحتاج إثباتًا مستقلًا؛ وجود lockfile وحده لا يثبت تطابق البايتات.

## المراجعة والاختبارات المطلوبة

كل تغيير يذكر المتطلب والسلوك قبل/بعد وثابت السلامة المتأثر ونتيجة التحقق. المراجعة تبحث عن فقد بيانات، تجاوز حد ثقة، تغييرات الحالة وإعادة المحاولة والتزامن قبل تجميل الأسماء. التغيير السلوكي يحتاج اختبارًا يحمي السلوك؛ لا اختبارات تنسخ التنفيذ ولا نسبة تغطية تستخدم كبديل عن سيناريوهات الأعطال.

| التغيير | شرط الدمج المستهدف |
| --- | --- |
| منطق محلي | تنسيق وفحص ساكن واختبارات وحدات/خصائص ذات صلة ومراجعة Engineering |
| بروتوكول/محلل | حدود ومدخلات مشوهة وعقود توافق وfuzzing موجه |
| قرص/حالات/تزامن | حقن أعطال واستعادة، تحقق بصمة، تداخل/تكرار/إلغاء، مراجعة Engineering مستقلة |
| أسرار/IPC/ترخيص/تحديث/FFI | مراجعة Security إضافية واختبارات سلبية؛ لا اعتماد ذاتي للتغيير |
| إصدار | مصفوفة المنصات والحزمة الفعلية وبوابات [الجودة](quality-and-release.md) |

CI الحالي يحتوي تنسيق Rust وبوابة الاعتماديات وClippy واختبارات وبناء واختبارات مختبر على الأنظمة الثلاثة. اكتمال فحوص TypeScript والأسرار والتبعيات والرخص وfuzzing وSBOM وتأهيل الحزم ما زال مستهدفًا بحسب حالة كل مكون. وجود CI لا يثبت تفعيل حماية الفروع أو فرض المراجعات في إعدادات المستودع. تظل عزل أسرار التوقيع ووظيفة إصدار محدودة الصلاحيات شروطًا للإصدار، وليست قدرات منفذة بمجرد ورودها هنا.

## الحالة التنفيذية

مرجع الحالة هو [سجل التطبيق](enterprise-implementation-status.md): يتعايش المحرك القديم والجديد، والأخير موصول بالنقل والتخزين والمجدول وIPC. toolchain والتبعيات مثبتة وتعريف CI موجود؛ الواجهة والترخيص الإنتاجي وSBOM والحزم الموقعة وتأهيل الأداء غير مكتملة. لا تستنتج حماية الفروع من نجاح workflow. الاستثناء الهندسي يسجل سببًا ومالكًا ومدة وإجراء تخفيف، ولا يسمح بتجاوز سلامة بيانات العميل أو إخفاء فشل أمني.

## استثناء التكامل الأصلي المعزول

تستخدم queue-secrets استدعاءات Windows DPAPI داخل وحدة صغيرة ذات واجهة Rust آمنة وتعليقات SAFETY وحارس يمسح الذاكرة ويحرر تخصيص النظام. المحرك يظل forbid(unsafe_code). هذا تكامل مع تشفير النظام، وليس خوارزمية تشفير خاصة. روجع مستقلًا في [مراجعة القدرات الأربع](four-features-review.md)، ويتوقف الحفظ المشفر على الأنظمة غير المدعومة دون بديل بنص واضح.

platform-files يعزل كذلك استعلام مساحة القرص عبر GetDiskFreeSpaceExW أو statvfs، مع معاملات محسوبة وقراءة مخرجات النظام بعد النجاح فقط. نتيجته استرشادية ولا تحجز مساحة. الكود الأصلي مراجع ضمن remaining-engine-review؛ بناء Windows لا يثبت سلامة التشغيل على بقية الأنظمة.
