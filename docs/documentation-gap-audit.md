# فجوات الوثائق ومعايير اعتمادها

التاريخ: 2026-09-23. النطاق: مراجعة الوثائق المحلية، مع مراجعتين مستقلتين للهندسة والأمان. هذه نتائج توثيق وليست مراجعة للكود أو إعادة تحقق من CI. لم تُعدّل ملفات التنفيذ. الدور الحالي وفق توجيه المستخدم: وضع المعايير وشروط القبول ومراجعة الالتزام بها؛ يلزم عكس هذا التغيير في وثائق المسؤوليات.

## النتيجة

توجد متطلبات مرقمة، معمارية مفصلة، نموذج تهديد، معايير هندسية، حالات قبول Q، وبوابات إطلاق G0–G5. النقص الأكبر هو تحويلها إلى مرجع متسق ومعتمد وقابل للتتبع. توجد كذلك عقود تشغيل وتجارية وخصوصية مطلوبة في النصوص ولم تُفصّل بعد. لا يلزم إنشاء ملف جديد لكل موضوع إن أمكن إغلاقه داخل الوثيقة المالكة الحالية.

**القبول:** لا يستطيع القارئ الوصول إلى حكمين متعاكسين عن القدرة نفسها في أقسام الحالة الحالية. إضافة فقرة جديدة أسفل الملف وحدها لا تغلق هذا البند. تُحسم حقيقة التنفيذ بفحص دليله عند التصحيح، لا باختيار أحدث عبارة تلقائيًا.

## DOC-02 — المرجعية المعتمدة والصلاحيات ونطاق Enterprise

**الأولوية: الآن.** المعمارية نسخة4 تصف نفسها مقترحة، وسجل التطبيق يصفها مرجعًا معتمدًا. قائمة التنفيذ تفصل السياسات المركزية كقدرات مشروطة، بينما المعمارية تدرج ADMX/MDM ضمن المراحل. كذلك وثائق الأدوار ما زالت تصف توزيع Product Owner السابق.

**المخرج:** سجل اعتماد يحدد النسخة الملزمة، وترتيب أولوية الوثائق، ومن يضع المعيار ومن ينفذ ومن يتحقق ومن يجيز الإصدار. لكل قرار مفتوح معرف ومالك وموعد حسم وبوابة تتأثر به. يُوثق هل الإدارة المركزية شرط إطلاق أم نطاق تجاري منفصل، دون اختلاق اعتماد تجاري من مجرد طلب تنفيذ المعمارية.

**القبول:** كل خلاف بين نصين له قرار مسبب، والاستثناء له نطاق ومالك وانتهاء وتخفيف. يُحسم أيضًا الالتباس بين سماح معايير الهندسة بـunsafe معزول ومراجع وبين وصف بعض حدود Windows بأنها تحتاج قرارًا بسبب منع شامل؛ هذه مراجعة للمرجعية، وليست تصريحًا بتخفيف الحماية.

## DOC-03 — مصفوفة تتبع المتطلبات والأدلة

**الأولوية: الآن.** PRD يطلب ربط البنود بمالك وإصدار ودليل، وقائمة التنفيذ:71 تؤجل إضافة حقول الحالة والمسؤول الفعلي ومعرف التغيير. التقارير موجودة، لكن لا توجد مصفوفة مكتملة تجمعها لكل متطلب.

**المخرج:** ربط `PR/NFR → DL → معيار قبول Q/بوابة G → اختبار أو تقرير → نسخة/حزمة → مراجع → حالة اعتماد`، مع المتبقي والعائق.

**القبول:** لكل متطلب إطلاق صف يمكن تتبعه، ويُميز بين مخطط ومنفذ ومتحقق منه ومؤهل للإصدار. لا يُغلق بند كامل بدليل يغطي جزءًا منه أو بمجرد عدد اختبارات إجمالي.

## DOC-04 — عقد قبول رقمي موحد ومصفوفة دعم معتمدة

**الأولوية: قبل تأهيل الأداء أو إعلان الدعم.** توجد أهداف فعلًا؛ خطة الجودة تصفها provisional والمعمارية تتضمن أهداف نقل وCPU وميزانيات أخرى. هذه ليست بالضرورة متعارضة، لكن يلزم توحيد مجال القياس: CPU لنواة واحدة مقابل الجهاز، ذاكرة buffers مقابل مجموع العمليات، خط أساس النقل مقابل تشبع الشبكة.

**المخرج:** جدول ملزم يحدد العتبة والحمل والجهاز والبناء وطريقة القياس والتكرارات وصاحب الاعتماد، وإصدارات OS والمتصفحات والمعماريات وأنظمة الملفات المدعومة والاستثناءات.

**القبول:** يستطيع فريق آخر إعادة القياس والوصول إلى حكم نجاح/فشل وفق العقد نفسه. لا تتحول أهداف مقترحة إلى وعود، ولا تتغير العتبة لإخفاء إخفاق دون قرار موثق.

## DOC-05 — عقود الحساب والدفع والاستحقاق

**الأولوية: قبل بناء التكامل التجاري.** WEB-01..08 وقواعد الترخيص موجودة. `web-commerce.md:27,36,45` يطلب أو يؤجل تفاصيل المصادقة والانتقالات؛ مدد التجربة والأجهزة والعمل دون اتصال ما زالت مقترحات.

**المخرج:** عقد تسجيل الدخول والعودة للتطبيق وتجديد الجلسة وإبطالها واسترداد الحساب، ومصفوفة أدوار وعمليات وموارد. جدول أحداث يربط الشراء والتجديد والفشل والإلغاء والاسترداد والاعتراض بحالة الدفع والاستحقاق وسلوك التطبيق، ويغطي الأحداث المكررة والقديمة والمتزامنة.

**القبول:** لكل حدث نتيجة متوقعة قابلة للاختبار، ولكل مدة أو عدد مقاعد حالة اعتماد صريحة. يظل الدفع في الموقع وفق قرار المستخدم. اختيار المزود أو السعر لا يُختلق لإغلاق الوثيقة.

## DOC-06 — سجل البيانات والاحتفاظ والحذف

**الأولوية: قبل استقبال بيانات العملاء.** مبادئ تقليل البيانات والحجب موجودة؛ `privacy-review.md:3` يحدد نفسه كمراجعة ضيقة للأداة الهندسية، لا سياسة بيانات للمنتج كله. وثائق الأمن والترخيص تطلب سياسة احتفاظ لم تُفصّل في جدول شامل.

**المخرج:** لكل حقل: الغرض، مكان التخزين، الحماية، الصلاحيات، مدة الاحتفاظ، الحذف، أثر النسخ الاحتياطية، وعقد حقول حزمة الدعم. تشمل القاعدة والسجلات والحساب والدفع والتفعيل والتشخيص.

**القبول:** يمكن تتبع دورة حياة كل فئة بيانات واختبار حذفها أو انتهاء احتفاظها، مع بيان الاستثناءات المعتمدة. حجب السجلات وحده لا يغلق هذا البند. ليست هذه المراجعة رأيًا قانونيًا أو اعتماد امتثال.

## DOC-07 — إجراءات الحوادث والتعافي والدعم

**الأولوية: قبل بوابة التشغيل G4.** `security-and-reliability.md:66` يطلب runbook وخطة الجودة تشترط استعادة الخدمة التجارية. المطلوب تفاصيل قابلة للتنفيذ تتجاوز المبدأ.

**المخرج:** درجات الحوادث ومسؤول القيادة والتصعيد وشروط إيقاف إصدار أو خدمة، وخطوات النسخ الاحتياطي والاستعادة والتحقق. تُحدد أهداف زمن الاستعادة وفقد البيانات المقبول RTO/RPO للخدمات المعنية بعد اعتمادها، مع بداية القياس ونهايته وإجراءات الدعم.

**القبول:** ينفذ شخص آخر تمرين حادث واستعادة بناءً على الوثيقة، ويُسجل الزمن والنتيجة والقيود. لا تُفرض SLA أو أرقام تعاقدية بلا قرار صريح.

## DOC-08 — دليل الإصدار والمفاتيح والترقية ودورة الدعم

**الأولوية: قبل بوابة التوزيع G3.** مبادئ التوقيع والفصل والتدوير موجودة في وثيقة الترخيص، لكن إجراءاتها ومسؤولياتها ودورة دعم الإصدارات تحتاج إكمالًا.

**المخرج:** إجراء إصدار مرتبط بالحزمة والمصدر، ملكية المفاتيح وتدويرها والتعافي من فقدها أو تسربها، قنوات التحديث، إيقاف التوزيع، توافق مخطط البيانات والترحيل والرجوع، ونهاية دعم الإصدارات. يشمل قرار انتقال المستخدم من المحرك القديم إلى الجديد وملكية بياناته إن شمله الإصدار.

**القبول:** تمرين إصدار وترقية وفشل ترقية وتعافٍ بتوقيعات وبيانات اختبار، مع تحديد ما يمكن الرجوع عنه وما لا يمكن. وجود توقيع أو هجرة منفردة لا يكفي لإغلاق دورة الإصدار.

## ما لا يُسجل كغياب وثائق

Proxy/PAC وSSRF وضوابط هوية Windows IPC وWriterPool وقياسات الأداء وغيرها لها متطلبات أو حدود موثقة بالفعل. عدم اكتمال تنفيذها لا يعني أن الوثائق أغفلتها؛ الفجوة التوثيقية هي غياب الحسم أو المالك أو الربط بدليل قبول عندما يغيب ذلك. كذلك نموذج التهديد ومعايير الهندسة وبوابات الإصدار موجودة، فتُستكمل بدل إعادة إنشائها من الصفر.
