# مراجعة حفظ الطابور والنقل المتوازي وإعادة المحاولة والسرعة المشتركة

التاريخ: 2026-09-21. المراجع: وكيل Engineering وSecurity مستقل عن منفذي المكونات. النتيجة: لا ملاحظات مانعة في الكود المفحوص ضمن النطاق الداخلي والحدود أدناه؛ القبول مشروط بنجاح دورة الاختبارات الموحدة المسجلة في حالة التنفيذ. هذه مراجعة كود وليست ادعاءً بنجاح اختبار لم يشغّل بعد.

## معايير المراجعة

- حفظ قبول المهمة وإعدادها قبل إقرار الأمر أو بدء الشبكة، وحفظ انتقالاتها دون إخفاء فشل SQLite. إعادة التشغيل لا تبدأ تنزيلات صامتة؛ المهام غير النهائية تحتاج استئنافًا صريحًا.
- تشفير كامل لقطة الطابور بما فيها الروابط قبل دخول SQLite أو سجل المعاملات. تنسيق بإصدار وحدود أحجام وعدد ومخطط متحقق، وقفل يمنع مالكين لنفس السجل.
- مكونات نطاقات متوازية محدودة العدد والذاكرة؛ تطابق التمثيل والنطاق والطول وETag والرابط النهائي لكل جزء. لا كتابة إلا للبادئة المتصلة الصحيحة، ولا تحرير للمهمة قبل تصريف العمال عند الخطأ أو الإلغاء.
- إعادة المحاولة محدودة العدد والمدة ولأخطاء عابرة معرفة، مع حفظ سياسة المحاولة والحالة. لا تكرار تلقائي لفساد البيانات أو تعارض الوجهة أو خطأ الصلاحية أو إعداد غير صالح.
- حد سرعة مشترك فعلي بين المهام مع حدود لكل مهمة، وإعادة حساب الانتظار عند التغيير الحي دون السماح بحصص قديمة تتجاوز السقف الجديد. الإلغاء يقاطع الانتظار مع حفظ البادئة الصحيحة.

## مراجعة حماية الطابور

القرار المقترح Windows DPAPI بنطاق المستخدم مع منع واجهة النظام التفاعلية، دون علم LOCAL_MACHINE. هذا يحمي البيانات المخزنة ضمن سياق تسجيل دخول النظام، ولا يمثل حماية من برنامج يعمل بصلاحيات المستخدم نفسه أو من استعادة سجل قديم. الملف ليس قابلًا للنقل المضمون بين الأجهزة؛ الملفات الشخصية المتجولة لها استثناءات بحسب إعدادات النظام. [توثيق Microsoft للحماية](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

استثناء unsafe محصور في crate `queue-secrets` لربط API النظام عبر تعريفات windows-sys، وليس تنفيذ تشفير خاص. شروط قبوله: أعمار مؤشرات صحيحة، أطوال قابلة للتحويل، تحرير LocalFree بحارس ملكية، مسح النسخ المؤقتة الحساسة قبل تحريرها، وعدم تحويل أي فشل إلى حفظ نص واضح. عدم توفر backend على نظام آخر يجب أن يرجع خطأ صريحًا؛ لا يجوز وصفه بأنه مخزن أسرار متعدد الأنظمة مكتمل.

طلبت المراجعة حدًا منفصلًا للنص وللمغلف المشفر بسبب كلفة DPAPI، وفحص إصدار وطول وبصمة داخل المغلف بعد فك التشفير وقبل استخدام البيانات. تذكر Microsoft أن بعض أشكال التلف قد تنجح مع مخرجات فاسدة، فلا يعتمد القبول على رمز خطأ محدد أو نجاح API وحده. البصمة الإضافية لكشف التلف ليست تفويضًا أو حماية من تعديل متعمد بواسطة مستخدم يملك حساب النظام. [توثيق فك الحماية](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptunprotectdata).

## دليل القبول المطلوب

تتطلب الدفعة تجارب فعلية للاستعادة بعد إعادة تشغيل المدير، وبقاء الروابط خارج النص الواضح في السجل، ورفض تلفه وازدواج المالك وفشل الحفظ؛ ونطاقات تصل بغير ترتيب، وخادم يتجاهل النطاق، وتمثيل يتغير، وإلغاء أثناء النقل؛ وأخطاء عابرة تنجح بعد محاولة محدودة وأخطاء دائمة لا تتكرر؛ وحد مشترك بين مهمتين وتغيير سقف أثناء الانتظار مع استجابة الإلغاء.

نتائج الاختبارات الموحدة والمنصة تسجل في [حالة التنفيذ](execution-status.md). المراجع لا يشغل Cargo بالتوازي مع منفذي الميزات. تبقى اختبارات فصل الطاقة الفعلي وتأهيل المنصات والحمل الطويل مستقلة عن الاختبارات المحلية لهذه الدفعة.

## ملاحظات المراجعة أثناء التنفيذ

- عولج ترتيب تصنيف أخطاء النطاق: استجابة 503 بلا ETag يجب أن تبقى خطأ HTTP قابلًا لتقييم سياسة المحاولة، لا خطأ تغير تمثيل. فحص تمثيل الملف يطبق على استجابات البيانات 200/206.
- أضيف التحقق من إعداد السرعة حتى للاستدعاء الذي يستقبل TrafficControl جاهزًا؛ التحكم المشترك هو مصدر وتيرة النقل الفعلية في هذا المسار الداخلي.
- طُلب جعل الوصول بغير ترتيب حتميًا في المختبر، وتأخير الإلغاء حتى بدء عدة طلبات نطاق فعلًا بدل إلغائها قبل انطلاقها، وإضافة اختبار 503 بلا ETag.
- فُحصت نافذة النقل: حتى ثمانية نطاقات، كل منها حتى 256 KiB؛ تجمع كاملة وتتحقق ثم تكتب بحسب الترتيب. عمال الشبكة لا ينفذون قرصًا، لذلك إيقافهم وتصريف JoinSet لا يقطع كتابة جارية. أخطاء النافذة تحفظ البادئة السابقة فقط.
- حدود الأصل الحالية تحصي المهام، وليس كل اتصال نطاق. يجب أن يذكر التوثيق أن عدد الاتصالات قد يزيد مع توازي أجزاء الملف؛ إثبات حد اتصالات إجمالي مختلف يتطلب منسقًا آخر.
- طُلب منع إعادة إشعار المعدل عند تعيين القيمة نفسها: الإشعار يعيد دفع زمن الشريحة، وتكراره عند حفظ مهام أخرى قد يؤخر النقل بلا داعٍ. تغييرات الحدود الحقيقية تستيقظ وتعيد حساب الكلفة؛ تظل دلالة القطعة الجارية محدودة ومعلنة.
- فُحص المنسق: يحفظ القبول قبل إقراره، ويحفظ Running وعدد المحاولات قبل إطلاق العامل. فشل الحفظ يغلق استقبال الأوامر ويلغي العمال وينتظرهم. لا يجوز وصف الإغلاق بأنه ناجح عند فشل الحفظ.
- عولجت الروابط الرمزية المعلقة: استخدام try_exists وحده قد يخفي وجودها قبل فتح ملف القفل أو قاعدة البيانات. فحص symlink_metadata يرفضها، مع بقاء افتراض مجلد خاص موثوق؛ لا حماية كاملة من تبديل المسارات المتزامن بواسطة مهاجم بصلاحيات المستخدم نفسه.
- عولج تحرير مخرجات DPAPI بحارس RAII يمسحها ثم يستدعي LocalFree، وتستخدم النسخ المؤقتة Zeroizing. روجعت تعريفات windows-sys 0.61.2 وzeroize 1.9.0 المحلية المثبتة؛ رخصتا الحزمتين MIT أو Apache-2.0، ولا build script في أي منهما. ليست هذه مراجعة ثغرات شاملة للتبعيات.
- عولج تكرار إشعار إعداد السرعة غير المتغير باستخدام send_if_modified، مع اختبار يكرر الإعداد أثناء الانتظار. الحد العام يصرف الشرائح بالتتابع داخل بوابة غير حاجبة، والإلغاء لا يترك حجزًا زمنيًا مستقبليًا.
- سياسة المحاولة لا تتجاهل طلب الخادم الانتظار: 429 واستجابات Retry-After لا تدخل إعادة المحاولة الآلية الحالية. يرجع Retry-After كفئة ServerBackoff دون كشف الرأس؛ جدولة موعده تلقائيًا ميزة لاحقة. أخطاء Network مجموعة منقحة قد تشمل حالات غير عابرة مثل فشل TLS؛ عدد المحاولات محدود ولا يحدث تخفيف للتحقق الأمني.

## قرار التقدم المستعاد وحدود القبول

نوقشت إعادة فحص مخازن النقل كلها عند فتح الطابور. القرار لهذه الدفعة الاحتفاظ بتقدم آخر لقطة كقيمة سابقة قد تتأخر بعد توقف مفاجئ؛ لا يستخدمها الناقل لتكوين Range أو تقرير النشر. الاستئناف يفتح مخزن النقل ويعيد التحقق من checkpoint ويحدث التقدم. هذا مقبول للنطاق الداخلي مع إيضاح الدلالة في واجهة مستقبلية؛ لا يوصف بأنه تقدم أعيد التحقق منه عند مجرد فتح القائمة.

فُحصت اختبارات فعلية لثماني حالات نطاقات، منها وصول بغير ترتيب، وهوية أو نطاق خاطئ، ورجوع آمن عند تجاهل Range، وإلغاء بعد بدء عدة طلبات ثم استكمال، وحد سرعة مشترك لعمال الملف، وتصنيف أخطاء الخادم. فُحصت ست حالات للطابور والمحاولات تشمل فتحه مجددًا دون إعادة إعطاء الروابط واستكمال الملفات، وقفل المالك الثاني، ورفض تغيير اللقطة، وحقن فشل حفظ يمنع الشبكة، ومحاولات محدودة، وإيقاف انتظار المحاولة مع تحرير خانة التنفيذ. كما فُحصت اختبارات ميزانية مشتركة بين نقلين فعليين وتغيير معدل أثناء النقل. أعداد التشغيل النهائية ونتائجها مرجعها حالة التنفيذ، وليست مجرد وجود ملفات الاختبار.

حفظ الطابور مشفر على Windows فقط؛ لا دعم مخزن دائم على الأنظمة الأخرى حتى توفير backend مناسب. اختبار إعادة الفتح منظم، وليس دليل قتل عملية أو فصل طاقة. يوجد حد سرعة مشترك لكل Manager، وليس بين عدة عمليات. تحديث حد المهمة أثناء انتظار حصتها العامة قد يترك شريحة سبق دفع كلفتها تحت الإعداد السابق؛ حجمها لا يتجاوز 64 KiB. إعادة حساب شريحة كبيرة بسرعة منخفضة جدًا قد تطيل انتظارها، لكن الإلغاء ورفع الحد يوقظانه. لا ادعاء حد لحظي دقيق على السلك أو عدالة أداء مثبتة تحت الحمل.

## نتيجة التحقق المركزي

أكمل الوكيل الرئيسي التحقق على Windows: 92 اختبار Rust مختلفًا و17 تجربة executable واختبار TLS، مع بناء وClippy لجميع targets بلا تحذيرات. نجحت الحالات المطلوبة أعلاه واختبار جامع للقدرات الأربع؛ الأرقام وحدود الدليل في [حالة التنفيذ](execution-status.md). لا ملاحظات كود مانعة متبقية ضمن النطاق الموثق.
