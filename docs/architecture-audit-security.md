# تدقيق المعمارية: الأمان وسلامة البيانات

التاريخ: 2026-09-21. مراجعة مستقلة للشفرة الحالية دون تعديل إنتاجي أو تشغيل Cargo. الوثيقة تميز الحقائق المقروءة من شروط التصميم التالي؛ ليست اعتماد جاهزية إطلاق. تقرأ مع [معايير الهندسة](engineering-standards.md) و[مراجعة التوسعة](remaining-engine-review.md).

## حقائق وتصحيحات من الشفرة

| المحور | الواقع الذي تأكد |
| --- | --- |
| النقل المتوازي | parallel.rs يجلب نوافذ حتى 8 أجزاء، كل منها 256 KiB، وينتظر النافذة ثم يرتبها ويضيفها كبادئة متصلة. لا توجد كتابة موضعية ولا سجل نطاقات مستقلة محفوظة. يمكن أن يؤخر الجزء البطيء النافذة، لكن الذاكرة محدودة |
| سلامة التخزين | Store يحفظ طول بادئة وبصمتها بعد sync_all ثم تحديث SQLite؛ يعيد حساب البصمة عند الفتح. SQLite مضبوط DELETE وFULL، وليس WAL. لا يجوز استنتاج أن تغيير journal وحده يزيل كلفة التحقق من الملف |
| البصمات | التحقق المحلي يكشف تغير البايتات مقابل الإيصال؛ لا يثبت أصالة المصدر دون expected_sha256 موثوق. قراءة كامل البادئة عند الفتح والتحقق الكامل عند النشر كلفتان حقيقيتان لهما سبب سلامة |
| النشر | Store ينشئ hard link إلى payload.part، والتصدير ينسخ إلى مؤقت في الوجهة ثم ينشئ hard link. لا يوجد fallback للأنظمة التي لا تدعم hard links. نتيجة ذلك خطأ قابل للدعم، لا استبدال صامت |
| المسارات | المخزن ودليل التصدير يرفضان symlinks، وعلى Windows يرفضان reparse points في سلسلة الآباء؛ قد يستبعد ذلك مجلدات شرعية يستخدمها العميل. فحص المسار ثم استعماله لا يثبت الحماية من مهاجم يبدل المسار بالتزامن |
| الشبكة | Client جديد لكل استدعاء download_controlled، وتشاركه أجزاء الملف عبر clone. هذا ليس Client جديدًا لكل Range ولا pool واحدًا لكل المدير. no_proxy يمنع proxy الموروث؛ إعداد proxy تجاري غير منفذ |
| الأسرار والتشخيص | RequestPolicy ينقح Debug ويربط الرؤوس بالأصل؛ الأخطاء فئات متحكم بها لأن reqwest قد يتضمن URL. الطابور DPAPI على Windows فقط؛ macOS/Linux يفشلان صراحة بلا plaintext fallback |
| دليل الأنظمة | سجل التنفيذ يذكر نجاح CI للأنظمة الثلاثة بعد إصلاح اصطدام مجلد الاختبار؛ نجاح ذلك لا ينفذ مخزن أسرار للأنظمة الأخرى ولا يثبت تحمل فصل الطاقة |

تكلفة تصدير 50 GB يجب تفكيكها بدقة: التصدير يحسب بصمة أثناء مرور النسخ نفسه، وليس مرورًا إضافيًا مستقلًا لقراءة النسخة النهائية؛ لكنه يستدعي Store::open وfinalize اللذين يعيدان فحص بيانات المصدر/الوجهة، فتوجد قراءات كاملة إضافية فعلًا. لا نحذف هذه الفحوص عشوائيًا؛ نبحث عن snapshot/handle متحقق قابل للاستهلاك داخل عملية واحدة لمنع التحقق المكرر، مع إبقاء كشف التعديل والنشر الصحيح واختبار أثر التزامن.

## كتابة موضعية واستعادة النطاقات

الكتابة الموضعية تحسين مناسب للتقييم لتجاوز انتظار أبطأ جزء، لكنها تغير نموذج المتانة. لا تكفي إضافة seek أو مشاركة File بين workers:

1. مالك واحد لجدول النطاقات وgeneration المورد؛ نطاقات نصف مفتوحة غير متداخلة مع checked arithmetic وسقف عدد/حجم. API موضعي مناسب للمنصة، بلا مؤشر ملف mutable مشترك. تجمع الكتابات عبر قناة محدودة أو طبقة تخزين متخصصة.
2. يتحقق كل رد من generation وETag وContent-Range والطول والتأطير قبل اعتماد نطاق؛ كتابة بايتات speculative لا تجعلها committed. نتيجة عامل قديم لا تستطيع تحديث جيل جديد.
3. لكل نطاق receipt يتضمن offset والطول والبصمة وحالة الحفظ. الترتيب: اكتمال الكتابة الصحيحة ثم مزامنة الملف وفق مجموعة checkpoint ثم commit لسجلات تلك المجموعة. عند commit ملتبس يغلق handle ويعاد الفتح. لا bit في bitmap قبل إثبات متانة البايتات.
4. الاستعادة تعيد التحقق من النطاقات المحفوظة ولا تعتبر file length أو sparse holes بيانات. لا تكتب فوق نطاق مصدق أثناء إعادة المحاولة؛ الفجوات يعاد طلبها. يجب منع اختلاف قواعد snapshot وجدول النطاقات، وضبط كلفة تعداد ملايين الأجزاء.
5. range hashes تتيح إصلاحًا أدق، لكنها لا تلغي I/O للتحقق من ملفات قابلة لتعديل خارجي. جمع SHA-256 للأجزاء لا يساوي SHA-256 القياسي للملف؛ التحقق النهائي للبصمة الموثوقة يظل قراءة مرتبة أو خوارزمية تجميع معيارية يحددها المصدر، دون تشفير مبتكر.
6. انتقال مخطط البادئة القديم إلى النطاقات يحتاج نسخة وإجراء migration آمنًا؛ لا تفترض أن 50% من حجم ملف موجود تعني أول 50% صالحًا. فشل الترقية لا يمحو المصدر القديم.

بوابة القبول: وصول بغير ترتيب، تداخل/فائض نطاق، تحديث generation أثناء النقل، short writes، فشل sync/commit، قتل العملية في كل حد، sparse/truncated/tampered files؛ يتطابق الناتج بايتًا ببايت مع المرجع. الأداء يقاس بعد هذه البوابات.

## نشر الملفات دون استبدال ودعم Junction

لا يصح استبدال hard_link بـstd::fs::rename مباشرة: rename يمكنه استبدال الوجهة، ووجود فحص exists سابق لا يغلق السباق. كما لا يعبر rename ملفات أنظمة مختلفة. [توثيق Rust](https://doc.rust-lang.org/std/fs/fn.rename.html).

التصميم الآمن يختار استراتيجية بحسب قدرات filesystem: مؤقت مملوك لنا داخل filesystem الوجهة، كتابة ومزامنة وتحقق، ثم عملية أصلية no-replace مدققة لكل منصة. لا fallback يرفع علم الاستبدال. عند غياب primitive مناسب، يرجع خطأ واضحًا أو يستخدم مسار حجز وجهة موثقًا لا يقدم الملف للمستخدم كمكتمل قبل النهاية؛ لا يوصف النسخ المباشر للنهائي بالنشر الذري.

يلزم publication intent بإصدار وحالات recovery تستوعب وجود المصدر فقط أو الوجهة فقط أو كليهما، وتتحقق من الهوية والبصمة قبل استكمال العملية. خطأ بعد إنشاء الوجهة لا يعني أنها غير موجودة. عبر الأقراص ننسخ ونزامن ونتحقق ثم ننشر، ولا نحذف المصدر قبل تحقق المرحلة النهائية. توافق exFAT/مشاركة شبكية والأقراص الخارجية يحتاج اختبارًا فعليًا؛ [Microsoft يفرق بين hard links وjunctions](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions).

رفض كل junction يرفع الأمان المحافظ لكنه يضر وجهات يختارها المستخدم مثل مجلد منقول لقرص آخر. التحسين يفصل **مجلد الحالة الداخلي** الذي يبقى خاصًا ومقيدًا عن **وجهة يختارها المستخدم** ويمكن حلها بإذن صريح. نثبت directory handle للوجهة المحلولة ونتحقق من هوية filesystem/الدليل ونستخدم عمليات relative-to-handle أو الآلية الأصلية المكافئة؛ canonicalize مرة ثم عمليات path وحدها لا تعالج TOCTOU. لا تمنح صفحة ويب اختيار جذر الكتابة. تختبر junction مبدلًا أثناء النسخ، وأبًا محولًا، واسم وجهة رابطًا أو ملفًا أجنبيًا.

تضاف حالات Downloads محول وOneDrive و`/tmp` الذي قد يكون alias على بعض الأنظمة. OneDrive reparse point قد يمثل placeholder أو مزود مزامنة، وليس مجرد junction إلى مجلد؛ السماح بكل reparse tags ليس سياسة آمنة. يجب تحديد الأنواع المدعومة وسلوك hydration/failure وتأثير تدخل خدمة المزامنة. على وجهة لا تدعم hard links مثل FAT/exFAT يكون فشل المسار الحالي فجوة توافق مؤكدة، ويحتاج محول نشر مجرب بدل check-absence ثم rename.

## Proxy والمصادقة وTLS وإعادة استخدام Client

إعادة استخدام Client تخفض كلفة إنشاء pool؛ المكتبة تصمم Client للمشاركة وتحتفظ بمجمع اتصالات داخلي. [reqwest 0.13.5](https://docs.rs/reqwest/0.13.5/reqwest/struct.Client.html). لا ينشأ singleton أعمى يخلط كل السياسات.

المطلوب مدير clients محدود العدد keyed بإعداد اتصال موثوق ذي إصدار: proxy endpoint ومعرف ملف اعتماده، trust-store profile، mTLS إن دعم لاحقًا، DNS/سياسة الشبكة وعزل المؤسسة. تستخدم معرفات سرية لا قيمة كلمة المرور ضمن مفاتيح debug/metrics. الاعتماد الخاص بالمصدر يبقى per-request؛ لا default Authorization أو Cookie jar مشتركة بين حسابات. تغيير سياسة proxy/الثقة يوقف إعادة استخدام pool القديم للطلبات الجديدة ويصرّف القديم وفق سياسة واضحة.

Proxy يحتاج إعدادات direct/system/explicit مفهومة، دون اتصال direct صامت عند فشل proxy إلزامي. Proxy-Authorization لا يرسل إلى origin، وAuthorization لا يرسل إلى proxy كبيانات تطبيق عبر HTTP غير محمي. TLS hostname/expiry/chain checks تبقى فعالة؛ دعم CA مؤسسي يكون ملف ثقة مصرحًا به، وليس accept-invalid-certs. الشهادة المؤسسية توسع من يقدر على قراءة الحركة ويجب إظهار السياسة للعميل.

سياسة العناوين الخاصة وتبديل DNS تتقاطع مع proxy: قد يحل proxy الاسم بدل العميل، فلا ندعي فحص destination IP محليًا يغطي الاتصال كله. طبقة نقل المتصفح المستقبلية تحتاج قرار origin/redirect/DNS عند كل hop وقناة مصادقًا عليها. المصادقة التلقائية للمؤسسة مثل NTLM/Kerberos ليست ضمن إرسال Bearer خام؛ تتطلب تصميمًا مستقلًا لتجنب تسريب اعتماد عبر أصل أو proxy غير مصرح.

## المراقبة دون تسريب

نعتمد أحداثًا ذات schema محدد: job ID محلي أو pseudonymous، attempt/generation، فئة الخطأ، status code، عدد البايتات، زمن الشبكة/القرص/commit، عمق الطابور وعدد الاتصالات. لا نسجل query أو fragment أو userinfo أو Cookie أو Authorization أو Proxy-Authorization أو قيمة ETag خام؛ أسماء الملفات والمسارات قد تكون معلومات حساسة أيضًا. لا يكفي مسح query لأن السر قد يقع داخل path أو رسالة خطأ.

تبقى rich errors داخل حدود منقحة: stable code مع أسباب مصنفة، دون طباعة Debug لسلسلة طلب/استجابة كاملة. labels لا تستخدم URL/host أو request ID غير محدود لتجنب تسريب ومعدلات cardinality عالية. حزمة الدعم تحتاج معاينة وتصديرًا اختياريًا واحتفاظًا معلومًا. [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) يوصي باستبعاد الرموز والأسرار والبيانات الحساسة من السجلات.

بوابة القبول: canaries في URL path/query، الرؤوس، أخطاء TLS/proxy، exception chains وcrash/debug outputs؛ لا تظهر في logs/metrics/support bundle. sampling والضغط الخلفي وحد حجم الملفات يمنعان تحويل التشخيص إلى استنزاف قرص.

## أسرار متعددة الأنظمة

DPAPI الحالي يحمي البيانات المخزنة ضمن نطاق المستخدم، ولا يضمن سرية من برنامج يملك الحساب. نجاح CI على macOS/Linux لا يغير UnsupportedPlatform. لا نقل تلقائي إلى مفتاح ثابت أو ملف plaintext لاستكمال الميزة.

التوصية للتقييم: واجهة مزود أسرار لكل نظام، واستخدام Keychain على macOS وخدمة أسرار النظام المتاحة على Linux، مع اختبار session مغلق أو خدمة غائبة أو user-presence مطلوبة وبيئة headless. إذا احتجنا تشفير snapshot كبير، يخزن مفتاح بيانات في مخزن النظام ويستخدم تشفير authenticated encryption بمكتبة معيارية مع nonce صحيح ونسخة مغلف وبيانات مرتبطة تربطه بالتطبيق/نوع السجل؛ اختيار مكتبة/provider قرار أمني مستقل، لا تنفيذ crypto خاص.

المطلوب migration لا يحذف النسخة القديمة قبل التحقق من الجديدة، وقفل يفصل فشل unlock عن تلف ciphertext، وإجراء إعادة تفعيل/إدخال اعتماد واضح بعد فقد مفتاح الجهاز. لا وعد باستعادة أسرار غير قابلة للاسترداد. الاختبارات تشمل rotation والاستعادة ورفض ciphertext معدل وتسرب plaintext، دون ادعاء حصانة من snapshot rollback أو مهاجم محلي صاحب صلاحيات.

## ترتيب العمل الموصى به

1. تثبيت عقود التخزين والنشر وإدارة الأخطاء وقياسات كلفة القراءة، مع اختبارات safety قبل أي تحسين يقلل التحقق.
2. تصميم writer موضعي وسجل نطاقات بإصدار وتجربة مقارنة قابلة للإلغاء والاستعادة؛ لا استبدال مباشر للمحرك المستقر دفعة واحدة.
3. محول نشر no-replace واختبارات ملفات الأنظمة، ثم وجهات junction بإذن وحد صلاحية مختلف عن مجلد الحالة.
4. مصنع Client وسياسات proxy/TLS وعزل الاعتماد واختبارات تسريب؛ المراقبة المنقحة تسند قياس أثر هذه التغييرات.
5. استكمال أسرار الأنظمة الأخرى قبل وعد طابور دائم متعدد الأنظمة. بوابة ربط المتصفح والأمان التجاري تبقى مستقلة.

هذه متطلبات تصميم قابلة للتنفيذ، لا ادعاء تنفيذ جديد. لم تجر تجربة أداء أو فحص ثغرات شامل أو اختبار أجهزة ضمن هذا التدقيق.
